id="i-roadmap-for-this-chapter">i. 本章路线图 </h3><p data-block="B025">我们首先学习每个 CTA 做哪些工作，以及这些工作如何分配给 B200 上的不同 CTA，见“工作并行化”小节。 </p><p data-block="B026">然后可选地绕道初学者入门，介绍逻辑表示与物理表示、指针和分块矩阵乘法。 </p><p data-block="B027">接着放大观察 B200 Attention 内核，讨论每个 CTA 内部发生的事情。 </p><p data-block="B028">后文会用图示更详细地解释这一切。这里先给出整体地图，随后我会提供与图示直接对应的代码链接。 </p><p data-block="B029">Attention 基础内核 </p><p data-block="B030">先来理解第一个内核。后续内核大多沿用本章引入的数学和 tcgen05 概念，所以本章会讲清贯穿全文的基础。这也是第一章比后续章节更长的原因。 </p><p data-block="B031">第一个内核是起点，能给出正确的数值结果，但效率远不及后续内核。它本身已经不简单，并使用了不少 Blackwell 特有功能，下面会逐步介绍。 </p><p data-block="B032">主要瓶颈 </p><p data-block="B033">Attention 基本上就是两次矩阵乘法，中间夹着一次 Softmax。Softmax 的 FLOPs 少得多，但它运行在 ALU 和 MUFU 单元上，而不是 Tensor Core 上。在 Blackwell B200 上，Tensor Core 吞吐量大致翻倍，指数运算单元却基本没变；FA4 论文称之为“不对称的硬件扩展”。因此，在我们的 tile 尺寸下，Softmax 消耗的周期数与算力很强的 MMA 差不多，成为该内核的主要瓶颈。多数优化从两方面着手：降低 Softmax 工作的代价，以及让它与矩阵乘法重叠，也就是把它隐藏在 MMA 执行期间。 </p><h3 data-block="B034" id="ii-work-parallelization">ii. 工作并行化 </h3><p data-block="B035">在讨论 B200 特有细节之前，先看工作如何划分。 </p><figure><img height="1368" src="./resources/iaroslavelistratov.github.io/assets/ch1/non-mma/ch1_17_5.png" width="2144"/></figure><p data-block="B036">可以把 Q、K、V 和输出张量都看成具有相同的形状：B、num_heads、seq_len、head_dim。 </p><p data-block="B037">我们将张量划分成 tile，使之能放入速度快但容量小的片上存储。如上图所示，tile 尺寸为 [128, 128]。 </p><figure><img height="1936" src="./resources/iaroslavelistratov.github.io/assets/ch1/non-mma/ch1_18.png" width="2832"/></figure><p data-block="B038">有多少个 O（输出）tile，就调度多少个 CTA；每个 CTA 生成一个 O tile。所有 CTA 合起来生成完整输出张量的全部 tile。CTA @ V_tile 累加到该 CTA 私有的 O tile 缓冲区中。这个私有 O tile 是运行中的累加器，在每轮 K/V 循环中更新。最后一轮结束后，CTA 对 O 累加器做归一化，并将完成的输出 tile 写入全局内存。 </p><p data-block="B040">如果现在还有不理解的地方，不用担心，下面会详细解释每一步。 </p><p Probabilities @ Values：使用微块执行 tcgen05，采用 MN-major 布局。 </li></ul><mark>阅读第 1 章时请始终记住这个整体图景；接下来会逐步放大，说明内核如何实现上述伪代码的每一步。</mark><h3 data-block="B048" id="iii-beginner-onramp--optional">iii. 初学者入门，可选阅读 </h3><p data-block="B049">本节可选。如果你已经熟悉分块矩阵乘法、内存布局、数据逻辑视图与物理视图的区别，以及如何用指针对内存进行索引，可以跳过。 </p><p data-block="B050">与分块矩阵乘法的相似之处： </p><p data-block="B051">先建立一个后面会用到的基本直觉：分块矩阵乘法。 </p><figure><img height="1220" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_1.png" width="3026"/></figure><p data-block="B052">普通分块矩阵乘法将两个操作数矩阵都拆成 tile，使较小的 tile 能装进高速但容量有限的片上存储，从而可以直接在片上多次复用每次加载的数据。每一轮沿归约维推进，图中为 K 维，将匹配的 A、B tile 相乘，再把部分结果累加到同一个 C tile。处理完所有 K tile 后，将这些部分结果相加，在数学上等价于不拆分 K 维的完整矩阵乘法。 </p><p data-block="B053">Attention 的形式与之相似，但并不完全相同： </p><ul><li data-block="B054">一般的分块矩阵乘法固定一个 C tile，沿其归约维遍历。 </li><li data-block="B055">Attention 固定一个 Q tile，沿 K/V 的序列维遍历。 </li></ul><p data-block="B056">引入布局： </p><p data-block="B057">现在，全局内存中存放着我们的数据 tile。 </p><p data-block="B058">假设要将一个 A tile 和一个 B tile 相乘。我们不想用软件手动遍历各元素，再用标量指令计算点积，因为那会非常慢。我们希望使用 Tensor Core，而在 Blackwell 上使用 Tensor Core，需要采用 tcgen05.mma 指令族。 </p><p data-block="B059">上图中的 tile_a 和 tile_b 看起来是二维矩阵，但它们只是已存数据的逻辑视图，实际内存是一维的。 </p><figure><img height="1302" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_3.png" width="3618"/></figure><p data-block="B060">因此，数据在物理内存中总是按照某种方式“排布”的。 </p><p data-block="B061">假设 GMEM 中的 A 操作数采用行主序。那么，各行在一维内存中依次连续存放，如上图所示。 </p><p data-block="B062">要在这段线性内存中找到某个 [row, col] 元素，需要从基指针出发，利用 stride 计算偏移量。 </p><p data-block="B063">例如有一个很小的 [2,2] 矩阵，我们想取得 my_matrix[1,1]。 </p><figure><img height="1690" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_2.png" width="3332"/></figure><p data-block="B064">这些二维 tile 总会以某种方式放入物理内存。布局就是把 [row, col] 这样的逻辑坐标映射到物理内存地址的规则；行主序就是一种布局。 </p><p data-block="B065">但我们想调用的 tcgen05.mma(tile_A, tile_B) 不能使用这种简单的行主序物理布局。它只支持少数几种非常特定的布局，不只是普通行主序或列主序。MMA 具体要求哪些布局，暂时还不重要，后面会讲。 </p><p data-block="B066">tcgen05 要求数据按特定布局组织，也就是按特定方式存放在内存中。此外，它不支持直接使用 GMEM 操作数，因为 GMEM 带宽太低，操作数必须先写入高速片上存储。 </p><p data-block="B067">本节要记住：我们需要在 SMEM 中，把 A、B 操作数排布成 tcgen05 支持的某一种布局。 </p><hr/><p data-block="B068">离开入门小节，回到主线： </p><p data-block="B069">如前两幅图和伪代码所示，每个 CTA 内的 Q 保持不变，每轮 K/V 循环计算： </p><ul><li data-block="B070">A）Q @ K.T -&gt; S </li><li data-block="B071">B）S -&gt; P </li><li data-block="B072">C）P @ V -&gt; O </li></ul><p data-block="B073">这就是沿 SEQ_LEN 遍历的 KV 循环每轮执行的三项主要计算。下面放大观察一轮循环，逐一讲解这三步。 </p><h3 data-block="B074" id="a-qkt-explaining-k-major">A）Q@K.T：解释 K-major </h3><p data-block="B075">一轮 K/V 循环内部：三步中的第 1 步。 </p><p data-block="B076">执行 QK 前，Q 和当前 K tile 必须已经在 SMEM 中。Q 由 CTA 加载一次，每轮 K/V 循环则加载新的 K tile。Q、K 使用相同布局，所以下面只画 Q 的复制过程，省略 K。 </p><figure><img height="1606" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_4.png" width="3032"/></figure><blockquote><p data-block="B077">注意：QK 矩阵乘法的图和代码片段采用常规矩阵乘法维度名称：Q[M,K] @ K[N,K].T = S[M,N]。这是局部矩阵乘法的轴名，不是内核输入全局张量的轴名。 </p></blockquote><p data-block="B078">前面说过，Blackwell 的 Tensor Core 通过 tcgen05 指令族使用。tcgen05.mma 要求操作数按特定布局组织，不能随意把 tile 从全局内存复制到共享内存后就执行 MMA。因此，我们必须将数据排布成 MMA 支持的布局之一。 </p><p data-block="B079">那么，具体应如何在 SMEM 中排布数据，才能让 MMA 使用？为简单起见，只说明 Q tile 从 GMEM 到 SMEM 的复制过程，K tile 同样独立执行此过程。在逻辑上，我们将 Q tile 纵向切成若干条带，图中示意为 4 条，再用 TMA 逐条从 GMEM 复制到 SMEM，见上图与<a href="#fn:2" id="fnref:2">脚注 2</a>。 </p><blockquote><p data-block="B080">为什么要这样切分 tile，而不是一次复制整个 tile？这是个好问题，先记在心里。我不想一次引入太多东西，等真正需要时再回来解释。现在只需记住，我们按条带复制。 </p></blockquote><p data-block="B081">复制完所有条带后，从 GMEM 到 data-block="B108">无需显式转置 K_tile。Q、K 均使用 K-major 布局。MMA 的 A 操作数直接读取 Q[m,k]；对于 B 操作数，tcgen05.mma 将已存 K tile 解释成 Q @ K.T 所需的 [k,n] 操作数。K-major 本身不意味着“转置这个操作数”：A、B 是不同的 MMA 操作数槽位，逻辑形状分别为 [M,K] 和 [K,N]，所以 MMA 对它们的解释不同。 </p><hr/><p data-block="B109">现在已经看过 QK 微步循环的代码。此前我们把 q_desc 和 k_desc 看作选择当前微块的类指针值。下面展开这些描述符还包含哪些布局信息，以及 MMA 如何用它们定位微块内部的数据。 </p><figure><img height="1294" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_8.png" width="2856"/></figure><p data-block="B110">这里其实还有更细的一层粒度。放大观察一个 Q 微块，即 BLOCK_M = 128、MMA_K = 16；相同逻辑也适用于 K 微块。 </p><p data-block="B111">微块本身由更底层的单元构成，称为 atom。CUDA 文档也称它们为“swizzle atom”。注意我们此时并未进行 swizzle；即使 swizzle 模式是 None，NVIDIA 仍将“swizzle layout atom”作为总称，见表 53。 <a href="https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/#tcgen05-smem-swizzle-mode" title="table 53">〔链接〕</a></p><p data-block="B112">atom 的大小取决于采用的规范布局。在这里，即 K-major 无 swizzle 布局下，atom 的尺寸为 (8, 8)，见<a href="#fn:4" id="fnref:4">脚注 4</a>。暂时仍可忽略布局细节，假定这是 tcgen05.mma 唯一支持的布局。 </p><p data-block="B113">从上到下总结，见上图图例：一个微块由两条条带组成，每条条带又由 atom 组成。我们需要理解 atom 在 SMEM 中的排布，但它们不是可以单独编程的 MMA 单元。发起 MMA 时，操作粒度仍是微块，而非单个 atom。 </p><blockquote><p data-block="B114">现在可以回答前面的问题：为什么要用 TMA 按 8 个元素宽的纵向条带复制 Q、K，而不是一次复制整个 tile？ </p><p data-block="B115">之前的条带宽度不是随意选择的，而是恰好一个 atom 的宽度。对 Q 而言，每条 (128,8) 条带是一叠纵向排列的 (8,8) atom。我们将 tile 切成这些条带，每次用 TMA 复制完整一叠，并在 SMEM 中将各叠依次存放。这就形成 tcgen05.mma 支持的 K-major atom 物理顺序。 </p></blockquote><figure><img height="1038" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_9.png" width="2382"/></figure><p data-block="B116">记住，前面说过，“黄色”循环每轮都向 tcgen05.mma 提供两个数据微块：一个 Q 微块和一个 K 微块。 </p><p data-block="B117">对于单个微块，无需给 MMA 提供其中所有 atom 的地址，只需提供第一个 atom 的基指针，见上图高亮部分。 </p><p data-block="B118">随着黄色循环推进，基指针从一个微块移向下一个微块。第一轮指向青色 atom，即微块 0 的起点；第二轮指向紫色 atom，即微块 1 的起点；如此沿 K 维推进。K 操作数描述符也做同样的事。 </p><p data-block="B119">但基地址只指向第一个 atom，因此直觉上，除了基地址以外，MMA 还必须知道如何从当前微块的第一个 atom 走到同一微块中的其他 atom。 </p><figure><img height="1054" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_10.png" width="2406"/></figure><p data-block="B120">为此引入 SBO 和 LBO，见上图。它们不会增加软件循环次数，而是描述同一微块中其他 atom 相对基指针的位置。SBO 告诉 MMA 如何到达同一条带的下一个 atom；LBO 告诉 MMA 如何到达下一条带中索引相同的 atom。 </p><p data-block="B121">对当前讨论的 K-major 无 swizzle SMEM 布局，每个 atom，以及每条纵向条带，宽度都是 8 个 BF16 元素，即 16B，因此： </p><pre tabindex="0"><code>SBO = 8 rows * 16B per row = 128B   // step over one atom
LBO = BLOCK_M rows * 16B per row = 2048B    // step over one complete slice of atoms
</code></pre><p data-block="B122">这里 LBO 就是 Q 复制循环中的 SLICE_BYTES，也就是 SMEM 中相邻纵向条带的偏移。一个 Q 微块包含两条条带，因此循环将描述符基地址增加 2 * SLICE_BYTES 字节，便可到达下一个微块。描述符地址以 16 字节为单位编码，所以除以 16 后，就得到上面代码使用的 q_desc_step。 </p><p data-block="B123">合起来看，软件循环把基指针从一个微块移到下一个，而 SBO、LBO 描述当前微块内部其他 atom 的偏移。 </p><h3 data-block="B124" id="b-online-softmax-explaining-s-p">B）在线 Softmax：解释 S -&gt; P </h3><p data-block="B125">一轮 K/V 循环内部：三步中的第 2 步。 </p><p data-block="B126">现在已讲完第一次矩阵乘法 Q@K.T，接下来进入内核的在线 Softmax 部分，即 S -&gt; P。 </p><p data-block="B127">在线 Softmax 的数学是标准内容，并非 B200 特有，已有很多讲解，所以这里不重新推导。我只概述所需状态更新，然后重点介绍 B200 内核如何实现。 </p><figure><img height="1402" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/non-mma/ch1_19.png" width="2768"/></figure><p data-block="B128">A 部分已简要见过 TMEM：Q @ K.T 的各个微步在那里累加出 S。现在放大观察 TMEM 本身，看看在线 Softmax 如何读取 S 并转换成 P。 </p><p data-block="B129">TMEM 的结构为 128 行、512 列，且必须显式分配。K/V 循环前，内核 1 为 S 分配 128 列，为 O 再分配 128 列。分配以列为单位，每列包含 128 个元素，因此分配 128 列就得到 [128,128] 的 FP32 TMEM 存储块。 </p><p data-block="B130">S 保存当前 K/V tile 的分数，每轮 K/V 循环都会覆盖。O 是运行中的输出累加器，后面 C 部分的 P@V 每轮向其中累加。tcgen05.alloc 将所分配区域的 TMEM 基地址写入共享内存槽 tmem_addr，再将该分配区域划分成 S、O 两个地址： </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-cpp" data-lang="cpp"><span style="display:flex"><span><span style="color:#66d9ef">int</span> TMEM_S_COLS <span style="color:#f92672">=</span> <span style="color:#ae81ff">128</span>;

遍历组织，其他状态更新大多融合进这三次遍历中。因此，可以把它理解为“对 TMEM 中的数据 tile 做三次遍历”。 </p><p data-block="B135">三次遍历可分为： </p><ul><li data-block="B136">两次遍历 S tile，共同用于生成 P。 </li><li data-block="B137">一次遍历 O tile，用于对 O 重缩放。 </li></ul><p data-block="B138">源码中的 O 重缩放位于两次 S 遍历之间。但由于两次 S 遍历的方式相同，我会把它们放在一起解释，再回来讲 O 重缩放。 </p><p data-block="B139">下面依次说明，随后对照代码。 </p><hr/><h4 data-block="B140" id="i-producing-p">i）生成 P </h4><p data-block="B141">先讲两次 S 遍历如何将 S 转成未归一化的 P，见<a href="#fn:5" id="fnref:5">脚注 5</a>；之后 P 会用于 P@V 矩阵乘法。为此，内核 1 对 TMEM 中 S 的每一行遍历两次： </p><ol><li data-block="B142">第一次计算各行最大值，为第二步提供数值稳定性。 </li><li data-block="B143">第二次减去行最大值并取指数，即 exp(S - new_rowmax)，生成未归一化 P。 </li></ol><p data-block="B144">在取指数前，先计算 S 每行最大值并从该行各元素减去它，称为 max trick，是 Softmax 实现常用的数值稳定技巧。S 中可能有很大的正分数，直接取指数可能溢出。减去行最大值，使 exp 输入都变成零或负数，在不改变 Softmax 结果的同时避免溢出。因此，不先减去 rowmax 就直接算 exp(S)，通常不具备数值稳定性。 </p><p data-block="B145">之所以要做两次遍历，是因为实现没有把所有 S 保留在寄存器中。第一次按块从 TMEM 加载 S、更新逐行最大值，然后复用同一组寄存器加载下一块。完成第一次完整遍历时，早先读取的数据已不在寄存器中。为了生成 P，必须第二次从 TMEM 读取 S，减去更新后的行最大值，再取指数。 </p><p data-block="B146">第一次 S 遍历：计算 rowmax </p><p data-block="B147">先看第一次遍历如何扫描 S 并计算逐行最大值，先看图，再看代码。 </p><figure><img height="1738" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/non-mma/ch1_20.png" width="2600"/></figure><p data-block="B148">只有 tcgen05 指令族能访问 TMEM，普通 load/store 不行。计算逐行最大值前，必须先加载 TMEM 中的数据，因此这里用 tcgen05.ld（ld 表示 load）将数据从 TMEM 加载到寄存器。 </p><p data-block="B149">从左到右读这幅图。我们分三个层次追踪 TMEM 遍历：整个 CTA、一个 warp、以及该 warp 中的一个线程。TMEM 中的 S tile 为 128 行、128 列。 </p><p data-block="B150">从 CTA 角度看，4 个 warp 分摊 S 的 128 行，每个 warp 负责一个 (32,128) 的行块。因此内核 1 使用 4 个 warp，以 32 行为单位覆盖并并行处理全部 128 行。 </p><p data-block="B151">但每个 warp 不会一次读完整个 (32,128) 块。那会导致寄存器溢出：寄存器不足以容纳四个这样的块，编译器就会把部分数据写入极慢的全局内存。为避免这一点，4 个 warp 各自以更小的 (32,8) 步长遍历自己的 (32,128) 块，见<a href="#fn:6" id="fnref:6">脚注 6</a>。因此需要一个遍历 TMEM 列的 for 循环。 </p><p data-block="B152">放大到单个 warp：每轮使用 tcgen05.ld 从 TMEM 加载 32 行、8 列的数据块。32 个线程共同参与一条加载指令，tcgen05.ld 是 warp 集体操作。它将加载的 32 行分配给 32 个线程，每线程一行。因此，每线程收到自己那一行的 8 个 FP32 值，32 个线程合起来持有完整 (32,8) 块。 </p><p data-block="B153">从一个线程角度看，每轮始终跟踪同一行，一次收到 8 个值；它遍历这 8 个值，保留目前见过的最大值。 </p><p data-block="B154">换句话说，加载是 warp 集体操作，而行计算是线程局部操作。每线程分批看到该行全部 128 个分数，每批 8 个，因此可在第一次 S 遍历中独立求出行最大值。这就是每个线程能在寄存器中维护自己的 tile_rowmax 标量的原因。 </p><p data-block="B155">每个线程在整个 K/V 循环中始终处理同一查询行。rowmax 和 rowsum 跨迭代保留，而 tile_rowmax、tile_rowsum 则对每个 tile 重新计算。 </p><p data-block="B156">因此，4 个 warp 合起来每轮处理 S 的一个 (128,8) 块，再向右移动 8 列重复。经过 128 / 8 = 16 轮，4 个 warp 遍历 S 全部 128 列。循环结束时，每个线程都持有某一 TMEM 行的最大值。 </p><hr/><p data-block="B157">代码调用 tcgen05::ld_32x32b_x8 辅助函数：.32x32b 表示加载 32 行 TMEM，每行一个 32 bit 值；.x8 表示在 8 列上重复该形状，并且仍是一条 tcgen05.ld 指令。于是每线程把 8 个 32 bit 行元素放入自己的 8 个寄存器。这就是图中的 (32,8) 块。 </p><p </span></span><span style="display:flex"><span>    <span style="color:#66d9ef">for</span> (<span style="color:#66d9ef">int</span> i <span style="color:#f92672">=</span> <span style="color:#ae81ff">0</span>; i <span style="color:#f92672">&lt;</span> <span style="color:#ae81ff">8</span>; <span style="color:#f92672">++</span>i) {
</span></span><span style="display:flex"><span>        tile_rowmax <span style="color:#f92672">=</span> <span style="color:#a6e22e">fmaxf</span>(tile_rowmax, s8[i]);
</span></span><span style="display:flex"><span>    }
</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span>}
</span></span></code></pre></div><p data-block="B159">那么，我们如何告诉这条指令要读取哪个数据块？ </p><p data-block="B160">S tile 的 [BLOCK_M, BLOCK_N] = [128,128] 分别对应 TMEM 的行和列。如前所示，4 个 warp 分别覆盖不同的 32 行区域，而每个 warp 的循环沿列推进。 </p><p data-block="B161">TMEM 地址是一个包含两个坐标的 32 bit 值，而不是普通字节地址： </p><pre tabindex="0"><code>[ upper 16 bits: row ][ lower 16 bits: column ]
</code></pre><p data-block="B162">PTX 将 TMEM 的行称为“lane”。对于当前加载方式，这两个坐标指定整个 warp 数据块的起始行和列，而不是分别给每个线程指定行列。 </p><p data-block="B163">地址构造如下： </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-cpp" data-lang="cpp"><span style="display:flex"><span><span style="color:#75715e">// first row of this warp's region:
</span></span></span><span style="display:flex"><span><span style="color:#75715e">// 0, 32, 64, or 96, depending on the warp_id
</span></span></span><span style="display:flex"><span><span style="color:#66d9ef">int</span> row_base <span style="color:#f92672">=</span> warp_id <span style="color:#f92672">*</span> <span style="color:#ae81ff">32</span>;
</span></span><span style="display:flex"><span><span style="color:#75715e">// bitshift to the upper 16 bits
</span></span></span><span style="display:flex"><span><span style="color:#66d9ef">int</span> trow <span style="color:#f92672">=</span> row_base <span style="color:#f92672">&lt;&lt;</span> <span style="color:#ae81ff">16</span>;
</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span><span style="color:#75715e">// inside the loop over S columns
</span></span></span><span style="display:flex"><span><span style="color:#66d9ef">int</span> taddr <span style="color:#f92672">=</span>
</span></span><span style="display:flex"><span>    trow                <span style="color:#75715e">// starting row, encoded in the upper bits
</span></span></span><span style="display:flex"><span>    <span style="color:#f92672">+</span> taddr_s           <span style="color:#75715e">// starting column of S
</span></span></span><span style="display:flex"><span>    <span style="color:#f92672">+</span> score_n8 <span style="color:#f92672">*</span> <span style="color:#ae81ff">8</span>;     <span style="color:#75715e">// current chunk's column offset within S
</span></span></span></code></pre></div><p data-block="B164">&lt;&lt; 16 将 row_base 移到高 16 位，低半部分为零。列号数值很小，自然位于低 16 位，高半部分为零，无需移位。下面每对括号表示 16 位： </p><pre tabindex="0"><code>row_base &lt;&lt; 16:  [row_base][  0   ]
column:          [   0    ][column]
sum:             [row_base][column]

(here, column = taddr_s + score_n8 * 8)
</code></pre><p data-block="B165">两个字段不重叠，因此用普通加法即可把行列组合成一个 TMEM 地址。 </p><p data-block="B166">注意，32 个线程传入相同的 taddr。对于这个加载形状，硬件利用线程的 lane ID，将 row_base + lane_id 行的数据分配给它。我们不自己把 lane_id 加到地址中，这与 ld.global 的普通逐线程寻址不同。例如 row_base = 32 时： </p><ul><li data-block="B167">lane 0 收到第 32 行的数据。 </li><li data-block="B168">lane 1 收到第 33 行的数据。 </li><li data-block="B169">…… </li><li data-block="B170">lane 31 收到第 63 行的数据。 </li></ul><p data-block="B171">这就是 warp 集体加载的含义：同一 warp 的 32 个线程共同参与同一条加载指令。这里它们使用相同 taddr，但每个线程收到自己那一行的 8 个值。 </p><p data-block="B172">循环推进时，trow 不变，而列偏移量每次增加 8。 </p><hr/><p data-block="B173">第二次 S 遍历之前：更新累计 rowmax </p><p data-block="B174">得到当前 S tile 的逐行最大值后，需要按在线 Softmax 定义更新累计 rowmax、rowsum。第一次遍历得到 tile_rowmax，即当前 S tile 中该行的最大值；第二次遍历使用的却是包含先前 K/V tile 在内的累计最大值。因此，第二次遍历前，要将 tile_rowmax 与旧 rowmax 合并，并对旧 rowsum 重缩放。这些都是寄存器中的逐线程标量更新，不是再遍历一遍 S。 </p><p data-block="B175">取两个最大值中的较大者，并计算重缩放因子： </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-c" data-lang="c"><span style="display:flex"><span><span style="color:#66d9ef">float</span> new_rowmax <span style="color:#f92672">=</span> <span style="color:#a6e22e">fmaxf</span>(rowmax, tile_rowmax);
</span></span><span style="display:flex"><span><span style="color:#66d9ef">float</span> rescale <span style="color:#f92672">=</span> <span style="color:#a6e22e">__expf</span>(rowmax <span style="color:#f92672">-</span> new_rowmax);
</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span>rowmax <span style="color:#f92672">=</span> new_rowmax;
</span></span><span style="display:flex"><span>rowsum <span style="color:#f92672">*=</span> rescale;
</span></span></code></pre></div><p data-block="B176">如果当前 tile 提高了累计 rowmax，那么旧 rowsum 是按之前的最大值计算的，必须乘以 rescale，才能让早先贡献与更新后的最大值一致。 </p><p data-block="B177">第二次 S 遍历会使用更新后的 rowmax 生成 P。同一个 rescale 也必须施加到旧 O 上，稍后在 ii 小节说明。 </p><hr/><p data-block="B178">第二次 S 遍历：生成 P 并更新 rowsum </p><p data-block="B179">现在有了更新后的累计行最大值，再遍历一次 S。分块重读 S，从分数中减去这些 rowmax，再安全地取指数，生成未归一化 P。 </p><p data-block="B180">TMEM 遍历方式与第一次相同，因此不另画遍历图。变化在于每线程对加载的 8 个值做什么：减去更新后的累计 rowmax、取指数、将结果加入该行的和，并将 P 写入 SMEM。 </p><p data-block="B181">仔细看看第二次遍历如何把 P 写入 SMEM。 </p><figure><img height="1540" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/non-mma/ch1_21.png" width="2112"/></figure><p data-block="B182">每读一块 S，就生成对应的一块 P，并写成 K-major SMEM 布局。这是后面 P@V MMA 所要求的布局。 </p><p data-block="B183">第二次 S 遍历每轮产生 8 列 P。相邻两块组成一个 16 列的 P 微块，由后续 PV MMA 微步消耗。 </p><p data-block="B184">TMEM 中的 S 本身不变。P 存入之前存 K 的同一个 SMEM 缓冲区。QK 结束后 K 已无后续用途，因此可以安全复用其空间存 P。 </p><p data-block="B185">下面是第二次 S 遍历的代码，从 TMEM 读 S，并向 SMEM 写 P。 </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-cpp" data-lang="cpp"><span style="display:flex"><span><span style="color:#66d9ef">int</span> row <span style="color:#f92672">=</span> row_base <span style="color:#f92672">+</span> lane_id;

</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span>rowsum <span style="color:#f92672">+=</span> tile_rowsum;
</span></span></code></pre></div><p data-block="B186">将 P 写入 SMEM </p><p data-block="B187">idx_kmajor_w8 计算每个 P 元素在熟悉的 K-major SMEM 布局中的位置，供后续 PV 矩阵乘法使用；该布局已在 A 部分介绍。辅助函数的具体实现并不重要，可以略过。这里需要 row 变量，因为这些是普通的逐线程 SMEM store，与 warp 集体 TMEM load 不同。 </p><hr/><h4 data-block="B188" id="ii-rescaling-o">ii）对 O 重缩放 </h4><p data-block="B189">回到 O 重缩放。源码中，它位于两次 S 遍历之间。前面已算出新的最大值基准，但旧 O tile 仍处于旧基准下。因此，执行 O += P @ V 前必须重缩放 O。在在线 Softmax 中，在旧 O 转换到当前最大值基准之前，通常不能安全地向 O 累加 PV。 </p><p data-block="B190">之前将当前 S tile 纳入了累计 rowmax。rowmax 的改变会改变未归一化 P 的尺度，也就影响累加到 O 中的 P@V 贡献。因此，在加入当前 P@V 贡献前，必须重缩放旧 O，让早先贡献与新的 rowmax 对齐。 </p><p data-block="B191">这是标准在线 Softmax 公式；这里唯一不同的是把它映射到 Blackwell B200 硬件。 </p><p data-block="B192">如前所述，rowsum 和 rowmax 是逐线程标量。O 不同，它是存于 TMEM 的完整 [BLOCK_M, HEAD_DIM] 部分累加 tile。 </p><p data-block="B193">因此，重缩放这些值需要读取 TMEM 中保存 O 的列，用刚从新旧 rowmax 算出的 rescale 乘它们，再写回 TMEM。必须写回，因为 O 仍是中间累加结果，并非最终输出；后续 PV 要继续在更新后的基准下累加。 </p><p data-block="B194">每线程对自己 O 行的全部值使用同一个 rescale。第一次 K/V 迭代跳过此遍历，因为还没有旧 O；第一个 PV 微步会初始化 O。 </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-c" data-lang="c"><span style="display:flex"><span><span style="color:#66d9ef">float</span> o8[<span style="color:#ae81ff">8</span>];
</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span><span style="color:#66d9ef">for</span> (<span style="color:#66d9ef">int</span> out_n8 <span style="color:#f92672">=</span> <span style="color:#ae81ff">0</span>; out_n8 <span style="color:#f92672">&lt;</span> HEAD_DIM <span style="color:#f92672">/</span> <span style="color:#ae81ff">8</span>; <span style="color:#f92672">++</span>out_n8) {
</span></span><span style="display:flex"><span>

</span></span></span><span style="display:flex"><span>        <span style="color:#f92672">+</span> out_n8 <span style="color:#f92672">*</span> <span style="color:#ae81ff">8</span>;       <span style="color:#75715e">// current chunk's column offset within O

</span></span><span style="display:flex"><span>

</span></span><span style="display:flex"><span>        o8[i] <span style="color:#f92672">*=</span> rescale;
</span></span><span style="display:flex"><span>    }
</span></span><span style="display:flex"><span>
</span></span><span style="display:flex"><span>    tcgen05<span style="color:#f92672">::</span><span style="color:#a6e22e">st_32x32b_x8</span>(taddr, o8);
</span></span><span style="display:flex"><span>}
</span></span></code></pre></div><p data-block="B195">这里使用与 S 遍历相同的 4 个 warp、行归属和 8 列分块。新内容是：在寄存器里完成重缩放后，用 tcgen05.st 将修正后的 O 写回 TMEM。 </p><p data-block="B196">此处省略 store 完成等待和同步。完整内核确保 O 的写入在 PV 使用累加器之前完成。 </p><p data-block="B197">现在 P 已在 SMEM 中准备好，O 也已在 TMEM 中重缩放，C 部分便可把 P @ V 加入 O。 </p><hr/><h3 data-block="B198" id="c-pv-explaining-mn-major">C）P@V：解释 MN-major </h3><p data-block="B199">一轮 K/V 循环内部：三步中的第 3 步。 </p><p data-block="B200">前面介绍了如何生成 P tile，现在要将它与 V tile 相乘。与 Q、K、P 都使用 K-major SMEM 布局不同，V 使用另一种 SMEM 布局。这就是接下来的主题。 </p><p data-block="B201">在内核 1 中，P_tile 由 Softmax 直接生成到 SMEM，因此下面的全局内存视图不画 P。 </p><p data-block="B202">实际内核在 QK 之前随 K 一起加载 V。这里才讲 V 的复制，是为了把它的 SMEM 布局与消费它的 PV 矩阵乘法放在一起讨论。 </p><figure><img height="1810" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_12.png" width="2626"/></figure><blockquote><p data-block="B203">注意：矩阵乘法图和代码片段以矩阵乘法为中心命名维度；实际内核源码则保留固定的 Attention tile 维度名。 </p><p data-block="B204">下面 PV 图采用常规矩阵乘法维度名：P[M,K] @ V[K,N] = O[M,N]。 </p><p data-block="B205">先退一步解释为什么把轴叫作 M、N、K。我对每次矩阵乘法分别使用常规 M/N/K 命名，因为这样单独观察每次乘法时，输入形状更容易理解。因此，这些是面向矩阵乘法的局部名称，不是全局张量 Q、K、P、V 固有的属性。 </p><p data-block="B206">同一个源维度在 QK、PV 中可以有不同的局部名称。K 维总指当前矩阵乘法的归约维：QK 中是特征维，PV 中则是 K/V tile 的行维。现在回到 PV 矩阵乘法。 </p></blockquote><p data-block="B207">Q、K、V 最初采用相同的全局内存布局，但内核根据各自 MMA 的消费方式，把它们放成不同的 SMEM 布局。为什么 Q、K、P tile 使用 K-major，而 V tile 要用下面介绍的另一种布局？ </p><p data-block="B208">因为 QK 需要把 K 看成转置后的矩阵；PV 的内部维度本来就匹配，V 无需转置。具体来说： </p><pre tabindex="0"><code>QK: Q[M,K] @ K[N,K].T
PV: P[M,K] @ V[K,N]
</code></pre><p data-block="B209">QK 中，K 按 [N,K] 存储，MMA 却将 B 操作数视为逻辑 [K,N]。因此 K 使用 K-major，使 MMA 能把已存 K tile 解释成逻辑转置操作数，而无需先构造另一份转置 K tile。 </p><p data-block="B210">PV 中，V 已经是 MMA B 操作数所需的 [K,N] 方向，所以使用 MN-major，让 MMA 直接消费 V，而无需先转置 V tile。P 是 [M,K] 的 A 操作数，仍使用 K-major。 </p><p data-block="B211">换句话说，对这些图使用的存储视图，我的速记方式是： </p><ul><li data-block="B212">K-major：归约 K 在右侧，如 Q[M,K]、K[N,K]、P[M,K]。 </li><li data-block="B213">MN-major 的 B 操作数：归约 K 在左侧，如 V[K,N]。 </li></ul><p data-block="B214">这只是我阅读这些操作数视图的速记方式，不是 K-major、MN-major 布局的正式定义。 </p><figure><img height="1840" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch1/mma/ch1_13.png" width="2508"/></figure><p data-block="B215">它们是同一次 PV MMA 的两个操作数。tcgen05.mma 允许独立选择 A、B 的 major mode，因此 P 可以是 K-major，V 可以是 MN-major。 </p><p data-block="B216">左侧 P 使用与 A 部分 Q 相同的 K-major atom 顺序。数字表示递增的 SMEM 地址。两种布局都采用 (8,8) atom，区别在于哪些 atom 紧挨着存放，这决定每次 TMA 调用复制多少数据。 </p><p data-block="B217">记住，对 Q，一次 TMA 调用复制整条纵向条带，并按正确顺序放置其中的 atom。V 的 SMEM 布局和 atom 顺序不同，因此需要重新考虑每次 TMA 调用应复制多少数据。 </p><blockquote><p data-block="B218">为什么不和 Q 一样，按更大的条带复制 V？ </p><p data-block="B219">Q 的同一纵向条带中，各 atom 在 SMEM 中连续存放，因此一次 TMA 可复制整个条带。 </p><p data-block="B220">看图中 V 的 atom 顺序：先沿第一个 8 行横带依次存放 atom，再向下移到下一个横带。因此，同一纵向条带的 atom 在 SMEM 中被其他 atom 隔开；一次 TMA 复制整条纵向条带，会把 atom 放错位置。 </p><p data-block="B221">那为什么不复制整个横带？我们使用的简单、无 swizzle 二维 TMA 复制会逐行存储矩形，得到普通行主序：一整行元素，接着下一整行。但目标布局要求先放完一个 (8,8) atom 的 8 行，再放下一个 atom。 </p><p data-block="B222">所以我们一次复制一个 atom，显式选择每个 atom 在 SMEM 中的落点。 </p></blockquote><p data-block="B223">下面是稍作简化的 </p><p data-block="B266">内核 2 改变 P 的存放位置：不再把 P 片段写入 SMEM，而是写回 TMEM。这是本章的主要变化。 </p><p data-block="B267">这一改动不会减少 SMEM 使用量，但为后续优化做准备。内核 1 把 P 放入 K 不再使用的 SMEM 槽，耦合了两者生命周期：QK 后不再需要 K，但它的槽要一直由 P 占用到 PV 消费完，这并不理想。可以给 P 单独分配 SMEM，但后续优化几乎需要整个 SM 的 SMEM 预算。因此，内核将 P 移到 TMEM，在不增加 SMEM 分配的前提下解耦生命周期，后面会据此继续优化。 </p><p data-block="B268">分配的 SMEM 不会减少，因为内核仍需要 Q、K、V 的存储空间。 </p><figure><img height="1396" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch2/1.png" width="3110"/></figure><p data-block="B269">进一步地，我们直接把 P 写进原来存 S 的区域，无需额外分配 TMEM。因为第二次 TMEM 遍历已经消费掉的 S 元素可以安全覆盖。 </p><p data-block="B270">因此，在内核 2 中，同一个 TMEM 槽的含义随时间变化： </p><ul><li data-block="B271">QK 后：槽内是 FP32 的 S。 </li><li data-block="B272">Softmax 第二遍：已消费的 S 块被打包的 BF16 P 覆盖。 </li><li data-block="B273">PV：将该槽作为 P 消费。 </li></ul><p data-block="B274">这确实耦合了 S、P 生命周期，但后面会看到，它不像 P、K 耦合那样棘手，见<a href="#fn:7" id="fnref:7">脚注 7</a>。 </p><p data-block="B275">TMEM 以 32 bit 存储单元组织，而 P 是 BF16，因此两个 P 值可以打包进一个 TMEM 单元。S 是 FP32，一个分数占一个 b32 单元。所以 P 所需的 TMEM 列数是 S 的一半。 </p><p data-block="B276">图中不同颜色箭头表示一次逻辑上处理 16 个分数的步骤。代码用两次 tcgen05.ld.x8 加载（橙色箭头），随后一次 tcgen05.st.x8 写入（绿色箭头）来实现。内核 1 按宽 8 的块处理 P；内核 2 每轮把两块合并，每行加载 16 个 FP32 S，生成 16 个 BF16 P。按宽 16 分组并非本质要求，见<a href="#fn:8" id="fnref:8">脚注 8</a>。 </p><p data-block="B277">回忆内核 1，生成 P 时按块遍历 TMEM，本章非常类似。新变化是把结果 P 块存入 TMEM：16 个 P 值打包进 8 个 b32 单元。因此 S 读指针前进 16 列，P 写指针只前进 8 列。每次 P 写入始终落在读指针之后，只覆盖第二次遍历已经消费的分数，因而不会破坏尚未读取的 S，图中也展示了这一点，见<a href="#fn:9" id="fnref:9">脚注 9</a>。 </p><p data-block="B278">S 占 128 个 TMEM 列，每次读取 16 列，共需 128 / 16 = 8 轮。结束后，低 64 个 b32 列包含完整的 128 列 BF16 P tile。P 只覆盖 S 缓冲区的一半，另一半保留不会再读的过期 S 值。下一轮 KV 循环的 QK 会用 S(i+1) 完整覆盖整个 S/P 槽。 </p><figure><img height="1322" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch2/2.png" width="3406"/></figure><p data-block="B279">PV 矩阵乘法不变：P[BLOCK_M, BLOCK_K] @ V[BLOCK_K, BLOCK_N] -&gt; O[BLOCK_M, BLOCK_N]。 </p><p data-block="B280">只改变了 A 操作数 P 的来源。内核 1 的 P、V 都从 SMEM 消费；内核 2 的 P 从 TMEM，V 从 SMEM 消费。 </p><p data-block="B281">内核 1 的 P 需要 K-major SMEM 布局和 SMEM 描述符。内核 2 直接用 TMEM 地址标识 P，不再为 P 使用 SMEM 描述符。 </p><p data-block="B282">K-major、MN-major 是 SMEM 布局，不用于 TMEM 操作数。V 仍是 MN-major 的 SMEM B 操作数。 </p><hr/><p data-block="B283">到这里已讲完 P 如何生成并写入 TMEM，而非第 1 章的 SMEM。现在再讨论 P@V，只是其中一个操作数 P 来自 TMEM。 </p><figure><img height="1522" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch2/3.png" width="3228"/></figure><p data-block="B284">记住，所有 MMA 图中的维度都采用常规局部矩阵乘法记号：A[M,K] @ B[K,N] = C[M,N]。 </p><p data-block="B285">PV 沿 BLOCK_K = 128 归约。与第 1 章一样，每次 MMA 消费匹配的 MMA_K = 16 微块：P[:, 16k : 16(k+1)] @ V[16k : 16(k+1), :]。8 次调用覆盖完整的 BLOCK_K = 128。为避免图面拥挤，只画前两次。 </p><figure><img height="1280" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch2/4.png" width="3092"/></figure><p data-block="B286">循环沿用内核 1 的逻辑 MMA_K = 16 微块顺序，但通过 TMEM 地址选择 P，而不是推进 SMEM 描述符。taddr_p + k * 8 指向下一个 128x16 P 微块的起点；每行的 16 个 BF16 值占 8 个 b32 列。V 描述符推进到匹配的 16 行，每次结果都累加到同一 O tile。 </p><p data-block="B287">P 现在由 tcgen05.st 产生，因此行线程在 PV 开始前必须等待这些 TMEM store，并执行 fence。这只是数据发布机制的小改动。 </p><p data-block="B288">所以内核 2 不改变 Softmax 数学、PV 归约顺序和高层调度。唯一语义变化是：QK 在 TMEM 生成 S，Softmax 将该存储区域变为 P，PV 直接从 TMEM 消费 P。 </p><div class="highlight-sketch"><div class="highlight-sketch-content"><p data-block="B289">内核检查点 </p><p swizzle 改为 SW128，以减少 bank conflict。P 留在 TMEM，因此不做 swizzle。 </p><p data-block="B302">已有很多资料解释 swizzle 的动机，这里不重复，因为目标是理解 B200 相关概念。只需知道，swizzle 在每个 atom 内置换 SMEM 地址，使 Tensor Core 访问更好地分散到各 SMEM bank，避免 bank conflict。下面讲 B200 特有细节，而非通用 swizzle 教程。 </p><p data-block="B303">Major mode 与 swizzle 是两回事，第 1 章已讨论。Major mode 指明每个 16B 元素内部紧密排列的是哪个矩阵乘法维度：K-major 为 K，MN-major 为 M/N；swizzle 则在该布局固定大小的 atom 内加入地址置换。因此先根据操作数角色选择 major mode，再决定使用 SW128，所需 atom 形状便由下面的 tcgen05 布局表确定。 </p><figure><img height="1294" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch3/0.png" width="2434"/></figure><p data-block="B304">下面把表中的单位换算成输入张量的数据类型 BF16 元素。 </p><figure><img height="1840" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch3/1.png" width="2966"/></figure><p data-block="B305">加入 swizzle 后，有两点值得讨论：（i）atom 变宽了；（ii）atom 内部发生了 swizzle。下面依次介绍。 </p><p data-block="B306">（i）atom 变宽 </p><p data-block="B307">NVIDIA 的 tcgen05 共享内存布局表以 128 bit 元素，即 16 字节，为单位，而不是 BF16 值。一个 BF16 是 16 bit，因此一个 128 bit 元素包含 128 / 16 = 8 个 BF16 值。 <a href="https://docs.nvidia.com/cuda/archive/13.0.0/parallel-thread-execution/#tcgen05-smem-swizzle-mode" title="tcgen05 shared-memory layout table">〔链接〕</a></p><p data-block="B308">文档要求只扩展 atom 的 leading dimension。表中 atom 维度按 (M/N, K) 排列，但这一点起初并不明显，见<a href="#fn:10" id="fnref:10">脚注 10</a>。 </p><p data-block="B309">K-major 的 leading dimension 是 K，也就是第二个轴： </p><pre tabindex="0"><code>(8,8) -&gt; (8, 8*8) = (8,64) BF16
</code></pre><p data-block="B310">Q/K 源 tile 已用 [M/N,K] 坐标绘制，因此其 K-major atom 看起来是 (8,64)。 </p><p data-block="B311">MN-major 的 leading dimension 是 M/N，也就是第一个轴： </p><pre tabindex="0"><code>(8,8) -&gt; (8*8, 8) = (64,8) BF16
</code></pre><p data-block="B312">对 V，按 NVIDIA 的 [N,K] 坐标，MN-major atom 为 (64,8)。而我画的源 V[K,N] 逻辑视图交换了两个轴，因此变成 (8,64)。这就是为什么在我的源坐标图中，两类 atom 都看似 (8,64)，实际却不是同一布局。 </p><p data-block="B313">先放大观察 Q@K 使用的 K-major 布局，稍后再回到 P@V 中 V 使用的 MN-major 布局。 </p><p data-block="B314">（ii）内部发生 swizzle </p><p data-block="B315">据我理解，引入 swizzle 后，不会置换 16B 元素内部的数据，而是置换这些 16B 元素本身。 </p><p data-block="B316">我们不关心逐行的具体置换，因为不需要手动计算。在 Blackwell 上，我们依靠 TMA 按 swizzle-128B 布局写入，tcgen05 按同一布局读取。 </p><p data-block="B317">如第 1 章所知，SMEM 布局必须与下游 MMA 一致。具体来说，在 TMA tensor map 中设置 CU_TENSOR_MAP_SWIZZLE_128B，使 TMA 以 swizzle 方式写 Q/K/V；再在 tcgen05 操作数描述符中设置匹配的 SW128 模式，让 tcgen05 知道如何消费。 </p><figure><img height="1620" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch3/2.png" width="2520"/></figure><p data-block="B318">先放大观察 K-major 布局，它用于 Q@K.T 的两个操作数。 </p><p data-block="B319">如前所述，复制进 SMEM 时希望按 (8,64) atom 排布。一个 K-major SW128 atom 宽 64 个 BF16，即 128B；完整 Q/K tile 的 HEAD_DIM = 128，即 256B。 </p><p data-block="B320">我们使用简单的二维 SW128 TMA map，无法一次复制整个 128 元素宽的 tile，再要求 TMA 将它视为两个独立 swizzle 的 128B 区域。CUDA 要求一个 SW128 TMA box 的内层维度最多 128B。在 Q/K tensor map 中，内层维度对应 HEAD_DIM，即图中横向维度。因此将 HEAD_DIM 切成两条宽 64 的条带。 </p><p data-block="B321">但这不意味着每个 (8,64) atom 都要单独发起一次 TMA。128B 只限制内层宽度；宽度设为 64 后，同一个 TMA box 可以向下覆盖 (8,64) atom。 </p><hr/><p data-block="B325">以上讲了如何告诉 TMA，复制到 K-major swizzle SMEM 布局时使用 swizzle。第二部分则是告诉 MMA 如何消费这种布局。 </p><figure><img height="1234" loading="lazy" MMA_K = 16 个元素为步长遍历 BLOCK_K。 </p><p data-block="B330">区别是现在逻辑上要拆分单个 atom：每个 atom 宽 64，而 MMA_K 只有 16。因此，128B 的 atom 宽度 / 32B 的 MMA 宽度 = 4 个微块。 </p><p data-block="B331">无 swizzle 时，我们把两列 atom 条带，我把 SBO 字段理解为：告诉硬件如何到达下一个 8 行 atom 中的对应片段。 </p><p data-block="B333">这里不使用 LBO。据我理解，这是因为： </p><ol><li data-block="B334">SBO 已经告诉硬件如何找到同一微块中的其他 atom 片段；另一方面， </li><li data-block="B335">推进描述符基地址，也就是 MMA 外层的软件循环，说明如何移到下一个微块。这两者已共同覆盖数据的两个轴。 </li></ol><p data-block="B336">因此，此处不需要 LBO 这样的额外偏移来描述另一个独立的遍历方向。 </p><hr/><p data-block="B337">回顾一下： </p><p data-block="B338">选定 major mode 后，SW128 决定一个 atom 的形状，以及其中 16B 元素如何置换。但单靠 SW128 并不能决定整个 tile 中全部 atom 的顺序。 </p><p data-block="B339">TMA 复制目标决定每个 atom 落在 SMEM 的哪里。MMA 一侧的描述符基地址、SBO，以及适用时的 LBO，必须描述相同排布；基地址由软件循环逐微块推进。否则 tcgen05 会读到错误数据。 </p><hr/><p Specialization（warp 分工） </h2><figure><img height="1020" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch4/0.png" width="2970"/></figure><p data-block="B349">目前内核使用 4 个 warp，各自可独立调度。但它们共 128 个线程在内核中多次同步，因此实际上是 CTA 范围同步。前面的内核已经使用可做更细粒度同步的 mbarrier，却仍让所有 warp 等待它们，几处 __syncthreads() 也仍同步整个 CTA，见上图。 </p><p data-block="B350">我们希望让工作者，也就是 warp，独立起来，以便后续并行并重叠它们的工作。首先需要让 warp 具备独立运行的能力，暂时还不分配独立工作。 </p><p data-block="B351">例如总共 128 线程、4 个 warp，目前在 load K/V(i) -&gt; QK(i) -&gt; softmax(i) -&gt; PV(i) -&gt; load K/V(i+1) 的每个箭头处全部同步。我们可以重排内核，让每个交接点只同步该操作真正需要的线程；例如仅同步 4 个 warp 中的两个，不阻塞另外两个。 </p><p data-block="B352">例如，加载生产者与 MMA 消费者通过屏障握手：生产者 warp 到达屏障，通知数据就绪 [^20]；消费者 warp 等待该屏障。其他两个 warp 无需参与，因此未来可以继续自己的工作，不被全局握手阻塞。这样，无关 warp 不必参与这次同步，也无需无谓暂停。 </p><p data-block="B353">内核 4 就做这种变换：不再像之前每个工作阶段都同步全部 128 线程，而是给各 warp 分工，只同步与当前交接真正相关的子集。 </p><figure><img height="1064" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch4/1.png" width="3366"/></figure><p data-block="B354">特别注意，内核 4 给 warp 分配了独立角色，却还没有给它们足够的独立工作来形成重叠。那些不参与某次握手的 warp 暂时仍没有独立工作可做，这会在后面实现。因此，虽然各角色拥有独立指令流，硬件操作也是异步的，主要阶段仍基本串行：加载 -&gt; MMA -&gt; Softmax -&gt; MMA。具体到前面的 load/MMA 握手示例，行处理 warp 即便不直接参与握手，也因为没有待执行工作而仍处于空闲。 </p><p data-block="B355">这显然不理想，我们需要给空闲 warp 找工作；后面几章会处理。我这样安排是为了循序渐进教学，而不是一次抛出所有优化。 </p><p data-block="B356">单独这项变化并不预期提升性能，因为它还没有增加并行工作量，但它为后续优化创造条件。概念上，内核 4 把整个内核拆成独立工作者：有些需要同步，其他的则具备独立前进能力。后续内核再给它们独立工作，把这种能力变成实际的工作重叠。 </p><p data-block="B357">要建立这些独立工作者，内核 4 需要比之前更多的 warp： </p><p data-block="B358">首先，仅并行完成 TMEM 中整个 S -&gt; P 就需要 4 个 warp。S 为 128×128，单个 warp 每次只能加载 32 行，为并行加载和处理 128 行，需要 4 个 warp。它们称为“行处理 warp”（row warps），负责 Softmax 与 O 重缩放，见<a href="#fn:11" id="fnref:11">脚注 Softmax(i+1) 与第二个 Q 的 PV(i) 重叠。正如第一章所说，Softmax 是整个内核的主要瓶颈，能与 MMA 重叠越多越好。 </p><figure><img height="1464" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch7/2.png" src="./resources/iaroslavelistratov.github.io/assets/ch7/3.png" width="3176"/></figure><p data-block="B434">但若简单把第一个 Q stage 的 QK(i+1) 搬到第 i 轮内，就会重复发起：第 i 轮末尾一次，第 i+1 轮开头又一次。第二个 Q stage 也有同样问题。 </p><p data-block="B435">所以还需要对内核做下面几项修改。 </p><figure><img height="1052" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch7/4.png" width="3814"/></figure><p data-block="B436">将每个 Q stage 的第一次 QK 从 for 循环剥离出来。类似内核 6 的加载流水线预填充，只是现在预填充的是计算流水线。 </p><p data-block="B437">这样，稳态循环就不会重复发起同一个下一 tile 的 QK。 </p><p data-block="B438">但由于循环前做了预填充，逻辑上在稳态循环后还要对应排空，完成两条 Q 工作流。因为最后一轮之后没有下一轮，若不排空，最后两个 PV tile 就不会执行。 </p><figure><img height="792" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch7/5.png" width="3588"/></figure><p data-block="B439">这就得到了本章最终设计。 </p><p data-block="B440">从视觉上看，像是把 QK、PV 顺序颠倒了，其实并没有。这里 q 是 Q stage 索引 0 或 1。稳态循环每轮先用 PqV(i) 完成当前 KV tile，再用 QqK(i+1) 开始下一个。对于任意单个 KV tile，顺序仍是 QqK(i) -&gt; softmax-q(i) -&gt; PqV(i)。我们只是移动了循环边界，tile 内部的顺序完全没变。 </p><div class="highlight-sketch"><div class="highlight-sketch-content"><p data-block="B441">内核检查点 </p><p data-block="B442">参见 <a data-block="B515" id="chapter-11--skip-o-rescale">第 11 章：跳过 O 重缩放 </h2><p data-block="B516">本章没有特别适合画图的内容，因此看一点伪代码。下一章继续图解。 </p><p data-block="B517">普通 Softmax 能看到整行，只需一次找到最终 rowmax，减去它，再取指数。 </p><p data-block="B518">在线 Softmax 每次处理一个 K/V tile，无法预先知道最终 rowmax。逐 tile 才逐渐看到整行，后面的 tile 可能出现更大最大值。因此，与普通整行 Softmax 不同，在线 Softmax 必须决定： </p><ul><li data-block="B519">每遇到一个更大最大值，都立刻切换过去吗？ </li><li data-block="B520">还是可以继续使用旧 rowmax？ </li></ul><p data-block="B521">前面各内核一旦发现更大最大值，就立刻采用： </p><pre tabindex="0"><code>new_rowmax = max(old_rowmax, tile_rowmax)
</code></pre><p data-block="B522">然后将全部旧状态改写到新基准下： </p><pre tabindex="0"><code>old O      *= rescale
old rowsum *= rescale
</code></pre><p data-block="B523">更新 rowsum 很便宜，但重缩放 O 需要再完整遍历 TMEM 中每行 128 个值。内核 10 每轮 KV 循环都执行 O 遍历，即便 scale 为 1。也就是说，最大值不变、rescale == 1 时，仍加载 128 个 O 值，乘以 1，再写回。这在数值上安全，却过于保守。 </p><p data-block="B524">内核 11 中，如果新 tile 最大值只比保留的 rowmax 略高，就继续使用旧 rowmax，不对 O、rowsum 做基准变换。只有差距足够大，才切换到新 rowmax，并把旧 O、rowsum 重缩放到新基准。 </p><p data-block="B525">跳过重缩放不会抹掉信息 </p><p data-block="B526">这一点我起初也没立即想明白，见<a href="#fn:18" id="fnref:18">脚注 18</a>。用一个小例子看看跳过 O 重缩放会发生什么，确认它不会导致信息丢失。 </p><p data-block="B527">假设决定为某个 tile 跳过 O 重缩放，具体阈值稍后讨论。暂设当前 tile 最大值比旧 rowmax 高 7.78。 </p><p data-block="B528">我们仍相对于旧 rowmax 计算 P： </p><pre tabindex="0"><code>P = exp2(scaled_S - kept_rowmax)
</code></pre><p data-block="B529">因此，新的最大值产生： </p><pre tabindex="0"><code>exp2(7.78) ~= 219
</code></pre><p data-block="B530">尽管跳过 O 重缩放，新最大值并未被抹掉，信息也未丢失。因为仍用旧 rowmax 计算 P，较大分数变成了约 219 倍的未归一化 P。这份差异就保存在更大的 P 中。 </p><p data-block="B531">更好的是，与选择重缩放的情况相比，整个内核最终结果完全不变。因为较大的 P 同时进入 Softmax 的两部分：分子 O 和分母 rowsum。 </p><p data-block="B532">相同的 P 值进入 Attention 的两部分： </p><pre tabindex="0"><code>O      += P @ V
rowsum += sum(P)
</code></pre><p data-block="B533">所以，对于前面 219 的例子： </p><pre tabindex="0"><code>O      += 219 * V_new
rowsum += 219
</code></pre><p data-block="B534">整个 K/V 循环后： </p><pre tabindex="0"><code>output = O / rowsum
</code></pre><p data-block="B535">新分数在 O 和 rowsum 中仍被视为约 219 倍大。最终除法没有抹掉这个相对差异，只是消去 O、rowsum 共有的尺度。 </p><p data-block="B536">那为什么还要切换基准？ </p><p data-block="B537">如果最终 O / rowsum 能处理共同尺度，似乎可以永远保留最初 rowmax。数学上，只要所有中间值不溢出，确实可以。例如旧 rowmax 已远落后于新值时： </p><pre tabindex="0"><code>gap = 20
largest P = exp2(20) = 1,048,576
</code></pre><p data-block="B538">最终答案在数学上仍等价，但 P、rowsum、O 的中间值会变得很大。如果溢出，最后除以 rowsum 的归一化显然不能撤销溢出。 </p><p data-block="B539">逐行决策如何映射到 warp 级 TMEM O 遍历 </p><p data-block="B540">是否切换基准由每行独立决定，但 TMEM O 的加载与存储是 warp 集体操作。因此实际实现如下： </p><div class="highlight"><pre style="color:#f8f8f2;background-color:#272822;-moz-tab-size:4;-o-tab-size:4;tab-size:4;-webkit-text-size-adjust:none" tabindex="0"><code class="language-c" data-lang="c"><span style="display:flex"><span><span style="color:#75715e">// convert the current tile's raw rowmax into base-2 exponent units

src="./resources/iaroslavelistratov.github.io/assets/ch14/1.png" width="2776"/></figure><p data-block="B583">把这称为一个“工作项”（work item），并抽象成图中形式。后续图以工作项为粒度。下一项优化改变的是 Attention 主体外部的生命周期，而不是主体本身，因此可以安全将主体抽象掉。 </p><figure><img height="1574" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch14/2.png" width="1992"/></figure><p data-block="B584">此前，如果工作项数量大于 SM 数量，即无法一次处理完所有工作，每个 SM 就依次运行多个 CTA：一个完成其工作项并退出调度，另一个处理不同工作项的新 CTA 接替。 </p><p data-block="B585">这些就是工作的“波次”（waves）。 </p><p data-block="B586">可以根据总工作量和每 CTA 处理量计算波次数： </p><p data-block="B587">以 SEQ_LEN = 4096 为例，对单个 batch、head，tile 边长为 128，Q、O 各有 4096 / 128 = 32 个 tile。每 CTA 处理两个，因此只有 32 / 2 = 16 个工作项。于是： </p><pre tabindex="0"><code>16 work items per batch-head
8 batches * 16 heads * 16 = 2048 total work items
</code></pre><p data-block="B588">对于 SEQ_LEN = 16384，单个 batch、head 的 Q、O 各有 16384 / 128 = 128 个 tile。每 CTA 处理两个，因此有 128 / 2 = 64 个工作项。 </p><pre tabindex="0"><code>64 work items per batch-head
2 batches * 16 heads * 64 = 2048 total work items
</code></pre><p data-block="B589">对于基准使用的三个形状，都会发起 2048 个独立 CTA，约 148 个能同时驻留，因此大约执行 14 波：ceil(2048 / 148 个 SM) = 14 波。 </p><p data-block="B590">通常称之为波次，但 CUDA 并不会等某一波 148 个 CTA 全部同时完成。某个 CTA 一结束，等待中的另一个就可能进驻空出的 SM，所以各 CTA 的推进时间会错开。 </p><p data-block="B591">于是每个 SM 大约依次处理 14 个不同 CTA：前一个完成并释放资源，后一个驻留。但这 14 次都重复支付相同开销：TMEM 分配/释放、CTA 生命周期状态设置、指针偏移、屏障初始化、CTA 调度等。 </p><p data-block="B592">SEQ_LEN 越短，CTA 固定开销越重要 </p><p data-block="B593">4K、16K 形状都要“重复 14 次”。来自 FA4 论文的三个基准形状恰好各有 2048 个工作项，因此同样承担 14 波固定成本。 </p><p data-block="B594">但 KV 循环从 4K 的 32 轮增长到 16K 的 128 轮，所以 16K 每波包含 4 倍有效工作： </p><pre tabindex="0"><code>KV-loop iterations = len_kv / BLOCK_N = 4096 / 128 = 32
KV-loop iterations = len_kv / BLOCK_N = 16384 / 128 = 128
</code></pre><p data-block="B595">输出工作项数量相同，但每项内部热循环工作量不同。短序列仍付 14 次相同初始化成本，KV 循环却更短，因此固定开销占比更高。与长序列相比，上述每 CTA 固定成本在较短的 4K 工作项中占总时间的比例更大。 </p><figure><img height="1500" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch14/3.png" width="2210"/></figure><p data-block="B596">如果一个 CTA 不只处理一个工作项，就可以只付一次初始化成本，将它分摊到多项工作，理想情况下分摊越多越好。为尽量摊薄成本，我们让 CTA 一直存活，处理自己大约 14 个工作项的序列。 </p><p data-block="B597">注意，无法摊薄的是：两个 Q 的加载、KV 遍历、输出写回、work ID 和指针计算。这些确实因输出工作项而不同；即便同一 CTA 处理多项工作，每一项仍需重新执行。 </p><p data-block="B598">CTA 不会锁步执行，因此图中的箭头长度不同。一个 CTA 中工作项的完成时间可以相对于其他 CTA 的进展发生偏移。 </p><p data-block="B599">跨工作项复用屏障 </p><p data-block="B600">此前屏障在 CTA 启动时初始化一次，贯穿其生命周期。内核 14 让屏障跨多个工作项继续工作。 </p><p data-block="B601">我最初的朴素实现，在工作项之间停止所有 warp，等待全部工作完成，再将屏障失效并重新初始化，然后才开始下一项。PTX 要求失效这一步，因为对仍有效的屏障调用 mbarrier.init 是未定义行为；重新初始化前必须确保没有 warp 仍在使用它。这样正确，却在工作项之间制造硬停顿：所有 warp 等待最慢者，全部工作彻底排空后才能开始下一项。 </p><p data-block="B602">为避免每个工作项边界都重复失效和初始化，内核 14 仅在 CTA 启动时初始化所有屏障一次，随后跨工作项持续轮转屏障 phase。旧 work_done 同步让所有 warp 等最慢者、将当前工作排空，保障重初始化安全，并保守地禁止任何缓冲区在整个工作项排空前复用。内核 14 改为跨工作项沿用已有 K/V 回收交接，再为 Q SMEM 增加 q_free。结合不再重初始化屏障，就无需全 warp 的 work_done 同步。 </p><p data-block="B603">因此，每个缓冲区在当前工作项的真正最后消费者用完后，就可释放： </p><pre tabindex="0"><code>Q SMEM:
    final QK reads Q(i)
    -&gt; q_free
    -&gt; load Q(i+1)

K/V ring:
    final QK reads K stage
    -&gt; refill K stage

    final PV reads V stage
    -&gt; refill V stage
</code></pre><p data-block="B604">这样，不再存在一个统一时刻，宣告 work_item(i) 结束、work_item(i+1) 开始。Softmax warp 仍在归一化并写 O(i) 时，加载 warp 已可加载下一份 Q/K/V；Q、K 就绪后，MMA warp 就能开始 QK(i+1)。 </p><p data-block="B605">因此，内核 14 同时引入持久化 CTA 生命周期与跨工作项流水线。 </p><figure><img height="1974" loading="lazy" src="./resources/iaroslavelistratov.github.io/assets/ch14/4.png" width="2302"/></figure><p data-block="B606">如图所示，内核 14 中每个持久化 CTA 并不处理连续 work ID。 </p><p data-block="B607">代码只是 work_id += gridDim.x; // 148 CTAs。静态 grid-stride 分配把每个工作项交给 148 个持久化 CTA 之一。每工作项覆盖相邻两个 Q/O tile，所以 CTA 前进 148 个工作项时，tile 索引前进 296。CTA 0 先处理 tile 0-1，再处理 296-297，然后 592-593。 </p><p data-block="B608">我也试过给每个 CTA 分配连续范围的工作项。上述跨步方式整体更快，但结果依赖形状，我尚未单独确定具体原因。我的猜测是，当 CTA 在接近的时间处理相同 batch-head 的不同 Q 对时，共享 L2 中的 K/V 复用会有帮助。 </p><p data-block="B609">图中展示的是每个 CTA 拥有哪些工作项，而非硬执行边界。如前所述，不同 warp 角色仍可让前一工作项的尾部与后一项的开头重叠。 </p><div class="highlight-sketch"><div class="highlight-sketch-content"><p data-block="B610">内核检查点 </p><p id="how-software-exp2-works">软件 exp2 如何工作 </h3><p data-block="B652">第 9 章“软件近似”的可选背景知识。 <a href="#chapter-9--software-approximations" title="Chapter 9 – Software Approximations">〔链接〕</a></p><p data-block="B653">内核 8 之后，指数输入已经使用以 2 为底的单位，我们计算 exp2(x)。 </p><p data-block="B654">数学上，exp2(x) = 2^x。 </p><p data-block="B655">因此，我们希望用 ALU 承担一部分 2^x 的计算。 </p><p data-block="B656">把 x 拆成整数部分和小数部分，分别求 2 的相应次幂，再相乘。由于 2^(a+b) = 2^a * 2^b，它等价于直接计算 2^x。 </p><pre tabindex="0"><code>integer_part = floor(x)
// always between zero and one
// by our definition above
fractional_part = x - integer_part

2^x = 2^integer_part * 2^fractional_part
</code></pre><p data-block="B657">例如： </p><pre tabindex="0"><code>x                   = -3.25
integer_part        = -4
fractional_part     = 0.75
</code></pre><p data-block="B658">这样拆整数部分很方便，因为 FP32 本来就有以 2 为底的指数位域。因此，只需调整多项式结果的指数位，就能施加 2^integer_part。 </p><p data-block="B659">但 2^fractional_part 不能像整数部分那么方便地计算，因为 FP32 指数位域只能按整步变化，例如可移动 -4 步，不能移动 0.75 步。因此，对小数部分采用多项式近似。按定义，fractional_part 总在 0 与 1 之间，所以只需近似 2^x 曲线中 x ∈ [0,1) 的一小段。 </p><p data-block="B660">指数位处理 2^integer_part，多项式处理 2^fractional_part。 </p><p data-block="B661">使用一个三次多项式近似这段曲线： </p><pre tabindex="0"><code>2^fractional_part
    ~= 1
    + c1 * fractional_part
    + c2 * fractional_part^2
    + c3 * fractional_part^3
</code></pre><p data-block="B662">可把多项式看成对弯曲程度逐渐增加的形状做加权混合。直线过于简单，二次项仍不够准确；三次多项式既足够灵活，求值又便宜： </p><pre tabindex="0"><code>1                    constant, flat component
fractional_part      straight-line component
fractional_part^2    quadratic curve
fractional_part^3    cubic curve
</code></pre><p data-block="B663">系数 c1、c2、c3 控制各分量的贡献强度。它们并非简单从指数曲线上采样得到，而是离线拟合选择，使加权曲线在 0 到 1 的区间尽量接近 2^fractional_part。 </p><p data-block="B664">这里使用一个小优化。朴素实现会先算 fractional_part**2、fractional_part**3，再分别乘系数并相加；显式构造这些幂需要两个额外乘法。我们改为将一次乘加的结果连续送入下一次乘加，因此整个三次多项式只需 3 条 FMA 指令。 </p><pre tabindex="0"><code>2^f ~= ((c3*f + c2)*f + c1)*f + 1
</code></pre><p data-block="B665">返回<a href="#chapter-9--software-approximations">第 9 章：软件近似</a>。 </p><h1 data-block="B666" id="acknowledgments">致谢 </h1><p data-block="B667">感谢 FlashAttention-4
