data-block="B041">在进入 <code>tcgen05</code> 之前，我想花一点时间介绍 Acquire-Release 语义。也许你还没注意到，我们其实已经大量使用了这种语义。</p><ul><li data-block="B042"><code>mbarrier.try_wait.parity{.acquire}.cta.shared::cta.b64</code></li><li data-block="B043"><code>mbarrier.arrive.expect_tx{.release}.cta.shared::cta.b64</code></li></ul><p data-block="B044">即使 <code>.acquire</code> 和 <code>.release</code> 是可选修饰符，指令默认就会采用正确的语义，我还是特意把它们显式写了出来。这源于我之前编写<a href="https://gau-nernst.github.io/amd-a2a/">多 GPU HIP 内核</a>的经历：跨 GPU 同步内存访问时，Acquire-Release 语义同样至关重要。我在<a href="https://gau-nernst.github.io/amd-a2a/#acquire-release-semantics">之前的博客</a>中作过更详细的解释，也可以参考 <a href="https://davekilian.com/acquire-release.html">Dave Kilian</a> 那篇写得很好的文章。</p><p data-block="B045">简单来说，Acquire-Release 配对保证：生产者线程中 Release 之前的所有操作，对消费者线程中 Acquire 之后的所有操作可见。在 TMA 的场景中，这意味着 <code>mbarrier_wait()</code> 一旦完成，也就是 <code>mbarrier.try_wait</code> 返回 1，我们就能确定 TMA 传输已经完成，后续访问共享内存的操作（例如 <code>tcgen05.mma</code>，或者简单的共享内存加载 <code>ld.shared</code>）都能看到最新数据。</p><figure><img alt="TMA 生产者与 tcgen05 消费者之间的 Acquire-Release 语义。" src="./assets/d6aa200d6017-acquire_release.svg"/><figcaption><p data-block="B046">TMA 生产者与 <code>tcgen05</code> 消费者之间的 Acquire-Release 语义。</p></figcaption></figure><p data-block="B047"><a href="https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-mbarrier-test-wait-try-wait">PTX 文档</a>中 <code>mbarrier.try_wait</code> 一节也再次确认了这一点，可以搜索“The following ordering of memory operations…”这句话。</p><blockquote><p data-block="B048">在已完成的 phase 中，CTA 内参与线程按照程序顺序，在具有 release 语义的 <code>mbarrier.arrive</code> 之前请求的、使用同一 mbarrier 对象的全部 <code>cp.async.bulk</code> 异步操作，都已执行完成，并对执行等待指令的线程可见。</p></blockquote><blockquote><p data-block="B049">对于该线程按照程序顺序，在具有 release 语义的 <code>mbarrier.arrive</code> 之后、<code>mbarrier.test_wait</code> 之前请求的内存访问，不提供顺序或可见性保证。</p></blockquote><h3 data-block="B050" id="decipher-tcgen05">解读 tcgen05</h3><p data-block="B051">下表概括了不同 GPU 世代的 MMA 指令之间的一些区别。</p><table><thead><tr><th>GPU 世代</th><th>MMA 指令</th><th>A/B 存储位置</th><th>C/D 存储位置</th><th>最大 BF16 MMA 形状（每个 CTA）</th></tr></thead><tbody><tr><td>Ampere (sm80)</td><td><code>mma</code></td><td>寄存器</td><td>寄存器</td><td><code>m16n8k16</code></td></tr><tr><td>Hopper Memory</td><td><code>m128n256k16</code></td></tr></tbody></table><p data-block="B052">(*) 在 Blackwell 上，A 也可以位于 Tensor Memory 中。</p><ul><li data-block="B053">有意思的是，<code>MMA_K</code> 仍然是 32 字节，而 <code>MMA_M</code> 和 <code>MMA_N</code> 则显著增大。这很合理：这种变化提高了 MMA 指令的算术强度，确保更快的计算不会受到内存瓶颈限制。</li></ul><p data-block="B054">我们已经知道如何用 TMA 将 A 和 B 加载到共享内存。由于 <code>tcgen05.mma</code> 直接操作共享内存，不需要再把它们加载到寄存器中，可以和 <code>ldmatrix</code> 说再见了。为了存放 MMA 结果，需要使用 <a href="https://docs.nvidia.com/cuda/parallel-thread-execution/#tensor-memory">Tensor Memory</a>：这是 Blackwell 中专门为此引入的一类新内存。Tensor Memory 的容量为 128x512，每个元素宽 32 位，正好可以存放 FP32 或 INT32 累加值。使用方式相当直接：</p><ul><li data-block="B055">分配（<code>tcgen05.alloc</code>）以列为粒度。换句话说，每次分配总会包含全部 128 行。</li><li data-block="B056">释放（<code>tcgen05.dealloc</code>）。内核退出前必须释放此前分配的空间，内核不会替你自动释放。</li><li>各种内存访问方式：<ul><li data-block="B057"><code>tcgen05.ld</code>：从 Tensor Memory 加载到寄存器。后面编写 epilogue 时会用到。</li><li data-block="B058"><code>tcgen05.st</code>：从寄存器写入 Tensor Memory。</li><li data-block="B059"><code>tcgen05.cp</code>：从共享内存复制到 Tensor Memory。</li></ul></li></ul><p data-block="B060">在代码中加入 Tensor Memory 行”，指的都是这个 Core Matrix。</p><ul><li data-block="B073">128 位等于 16 字节。</li><li data-block="B074">8x2 tile 和 8 行，显然都对应 Core Matrix 的 8 行。</li><li data-block="B075">8x2 tile 对应 32 字节的宽度，恰好等于 MMA 形状的 K 维大小；对 data-block="B108">我大致知道，应该使用 TMA 支持的最大 swizzle 粒度：128 字节。接下来就研究它。这里不会全面展开 swizzle 的原理，更详细的解释可以参考其他文章。</p><p data-block="B109">Swizzle 是一种避免共享内存 bank 冲突的技术：它将特定访问模式要加载的数据分散到全部 32 个内存 bank 中。我之前做过一个 <a href="https://gau-nernst.github.io/bank-conflict/">Bank Conflict Visualizer</a> 来演示这一点。它默认展示 BF16 情况下 <code>ldmatrix</code>（<code>8x16B</code>）的访问模式，该模式存在 bank 冲突。Swizzle 通常会将列索引与行索引进行 XOR，使同一行中的元素在各列之间发生置换，并且不同行采用不同的置换。</p><p data-block="B110">2026-04-08 更新：本节已修订，以正确描述 TMA 的 swizzle 行为。</p><p data-block="B111">TMA 的 swizzle 以 16 字节为粒度。不同 swizzle 模式指定要重排的数据块大小；严格说并不完全如此，后面会进一步解释。例如，<code>CU_TENSOR_MAP_SWIZZLE_128B</code> 表示一个 128 字节的数据块内有 8 个 16 字节单元，这 8 个单元根据行索引进行置换。可视化如下。</p><figure><img alt="TMA 支持的几种 swizzle 模式。" data-block="B118">然后使用图中给出的 swizzle 函数。</p><p data-block="B119">上图准确展示了数据如何重新分布，但它与 TMA 描述符编码的逻辑布局并不完全对应。<a data-block="B142">我们真的需要理解 swizzle 吗？注意，代码里没有任何手动计算 swizzle 的地方。我们只是在 Tensor Map 编码时设置 <code>CU_TENSOR_MAP_SWIZZLE_128B</code>，并在共享内存描述符中把第 61-63 位设为 2。换句话说，只要 TMA 与 <code>tcgen05.mma</code> 对 swizzle Modal 不提供 ncu 访问权限。</li><li data-block="B146">我能想到的一个可能原因很简单：TMA 最内层维度更大时，全局内存加载更快。对 3D TMA 而言，v1 和 v2 的整体形状都是 <code>[BLOCK_M, BLOCK_K]</code>。这进一步说明，TMA 引擎对某些访问模式可能比其他模式更高效。为 TMA 做微基准测试应该是个有趣的项目，也许已经有人做过，只是我不知道。同样，这个解释也可以用 ncu 验证。</li></ul><h2 data-block="B147" id="pipelining">流水线</h2><p data-block="B148">下一步自然是实现流水线。这里先采用“Ampere 风格”：N 级流水线意味着始终有 N
