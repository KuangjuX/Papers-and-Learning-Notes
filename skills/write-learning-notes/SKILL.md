# 撰写学习笔记

写出脱离原始对话也能独立阅读的笔记。这个仓库主要保存论文、理论学习和开源项目学习笔记。先判断本次属于哪一类，再应用对应规则；混合主题可以组合使用。以用户**本次**指定的主题、深度和范围为准，不把上一篇笔记的内容取舍当成通用要求。

## 确定范围

在本仓库新增或更新正式笔记时，先执行根目录 `AGENTS.md` 的 Issue 与 PR 工作流：创建或复用 Issue，再在独立分支编辑，通过关联 PR 合并；未读完论文的 Issue 跨多次 talk 和 PR 保持打开。

1. 确认这篇笔记要解释什么、依据哪些材料。整理现有笔记时先读原文；涉及论文时核对原论文及其附录，涉及项目时核对实际源码与版本。
2. 查看相邻笔记和仓库约定，确定存放位置、语言、链接方式与详略。若用户本次要求与既有习惯不同，以本次要求为准。
3. 根据学习目标选择内容。用户明确列出要保留的几方面结论时，以这些方面为正文边界，不为套用完整模板补齐其他章节。只整理已讨论且用户关注的内容；必要的查错与补证据紧贴原问题，不顺带展开未讨论或明确暂不关注的技术分支。某次排除的主题只约束该次范围，不变成以后永久排除的规则。

## 阅读入口：Issue 导读、用户记录、讨论后阶段性整理

- 用户指定论文并开始阅读协作时，默认由 AI 按标题、别名、arXiv/DOI 或 Zotero key 查找已有主笔记和同一论文的未关闭 Issue。优先复用；没有对应 Issue 时创建，写明论文来源、已有主笔记链接或拟用路径、阅读范围与完成条件，并将 Issue 链接交给用户。未读完的后续讨论继续使用同一 Issue。
- AI 先读取原文的 Introduction、Background 或对应章节，在 Issue 提供简短导读：具体问题、必要背景、已有方法的困难，以及作者提出的主要思路。附原文链接和章节或页码；按需解释或翻译关键短段，不默认逐段翻译整章或预写完整笔记。区分作者主张与 AI 解读，尚未核对的实验结论只作为作者主张介绍；原文不可获取时说明材料缺口，不凭标题补写。复用 Issue 时先读已有导读与讨论，只补缺失内容，保留用户原有记录。
- 导读是阅读入口，不替代用户自己的理解骨架，不作为用户已理解或读完的依据。用户随后记录自己的理解和问题，AI 围绕这些内容讨论、查错和补证据；不把导读直接当作用户观点，或仅凭导读生成最终主笔记。
- 用户在 Issue 正文或评论中随手记录骨架、引文、截图和疑问；不要求预先写成文章，也不为此默认创建空白正文或工作分支。Issue 保留探索过程，唯一主笔记保存按问题和机制组织的解释，不维护两份同步全文。用户选择直接写 Markdown 时，沿用已有主笔记；需要 AI 准备文件时再建立工作分支，只放来源和必要提示，不替用户预填结论，空白模板不进入正式导航。
- 用户要求笔记更新后同步 Issue 时，更新已有 AI 摘要和主笔记链接，避免重复追加同一结论；保留用户手写正文和评论，不用 AI 整理覆盖它们。
- 引文和截图尽量带上论文版本、章节、图号或 PDF 页码及原文/Zotero 定位链接，并说明对应的理解或疑问。原文、用户判断和 AI 解读分开；定位不全时，整理阶段先核实，无法确认则保留不确定性，不猜测出处。
- 讨论后，用户要求阶段性整理时，先读取 Issue 正文、相关评论、图片和已有主笔记，再按下节协作要求查错、补证据、去重，将已澄清的解释、个人判断与尚未解决的知识疑问整合到对应章节，不按评论顺序拼接全文。不要求读完整篇才整理，也不替未读部分填充结论。正式文章只保留必要短引文与相关解释；需要保留的图片放到主笔记旁的 `images/` 等配套目录并使用相对路径，注明原图来源与图号，保留坐标轴、图例及影响判断的实验条件。只在 Issue 中记录材料不触发自动发布。
- 整理通过 `AGENTS.md` 的分支与 PR 流程交付；未读完或状态不确定时以 `Refs` 关联并保持阅读 Issue 打开。一次增量合并不等于阅读完成；合并后清理该次工作分支，下一次整理从最新默认分支新建分支，继续关联同一阅读 Issue。

## 协作方式：用户先写理解骨架，AI 查错、补证据和去重

- 用户的骨架可以只是要点：具体问题、关键设计或数据流、收益与代价，以及已理解、推测和仍有疑问的部分；不要求先写成完整文章。以这些内容确定笔记要回答的问题，不另起一篇通用综述覆盖用户的思路。
- AI 先检查技术错误、遗漏的前提、推理跳步和证据是否足以支持判断，再对照论文、固定版本源码或实验记录补缺。补充应紧邻相应论断，保留来源和适用条件；无法核实就说明缺口，不用流畅解释代替证据。
- 保留用户的个人判断、独有推导、算例和知识疑问。与证据冲突的判断应据实纠正，并在交付说明中指出重要纠正及依据；未能证实或证伪的判断保留为个人推论。不要因追求统一口吻而抹去这些内容，也不要将 AI 新增推论冒充用户观点。
- 用户要求只保留事实时，正式笔记只写原文、源码或公开实测能支持的内容；删除 AI 猜测、未经验证的性能归因、成本估算和自行推导的性能比例，不以“可能”“推测”标注后继续保留。公开性能数据保留来源与已披露测试条件，不将算子吞吐或峰值占比改称模型 MFU。用户手写内容仍保留在原处。
- 去重时合并重复结论，保留不同前提、反例与证据差异。默认不扩充篇幅，不为凑齐结构添加背景、同义复述或泛化总结；每处新增内容都应解决一个具体理解缺口，必要技术细节不因追求简短而删除。
- 未解决的知识疑问放在相关机制旁，说明尚不确定的条件；它们属于理解边界，不是应删除的学习待办。已有充分证据解答时，将答案与依据整合进去，不把已解决的问题继续写成悬而未决。
- 没有提供骨架时，先使用已有笔记或讨论；遵循用户当次明确的起草、扩写或整理要求，不强制先索要草稿。材料不足时缩小结论范围，并指出需要用户判断的具体问题。

## 把问题、设计、代价与证据连成解释

- 对关键设计，先说明已有做法遇到的具体瓶颈或约束，再解释所选机制如何解决它、引入什么成本或限制，以及哪些推导、源码或实验支持这一判断。这是叙述的因果关系，不要求设置四个固定标题；简单知识点可用一段讲清。
- 先定义对象的含义和职责，再引入符号、数据结构与函数。公式说明机制，源码说明落地方式；将二者放在相关设计旁，不另起一套重复的“理论讲解”和“源码讲解”。表格用于并列比较，不能替代设计之间的因果解释。
- 让章节之间有实际依赖：前一设计留下的困难引出后一机制。例如 KV 复用改变任务划分，进而需要反向索引、负载均衡和局部结果合并；不能只在几个独立知识点之间添加“因此”就声称存在因果关系。
- 证据贴近被验证的取舍：消融说明改变该设计后的质量变化，源码说明特定版本的行为，成本模型说明特定假设下的数量关系。性能结论交代工作负载、硬件、指标、基线和额外开销；没有分项消融或测量时，不把整体加速归因于某个机制，也不补造证据。
- 每段应增加事实、解释、推导步骤、算例或证据。一个结论在主要位置讲透，后文仅补充差异或交叉引用；删去换说法的重复、泛化提醒和重复总结，同时保留必要的因果衔接及独有细节。不以字数、删减比例或表格数量衡量质量。

写法参考：[NVIDIA — Sparse Attention in TensorRT LLM](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog17_Sparse_Attention_in_TensorRT-LLM.html)。借鉴其连接设计动机、接口语义、实现代价与实验解释的方式；不照搬宣传措辞、产品目录或其他系统的技术结论。

## 论文笔记

- **一篇论文对应一篇持续更新的正式文章**。不同 talk、会话、来源或讨论主题不是新建笔记的理由。保存前用论文标题、别名、arXiv/DOI 或 Zotero key 检索主题索引和已有文件，确定唯一主笔记；仅当确实不存在时创建。
- 新讨论按理解依赖整合进已有章节：背景与问题、洞察与设计、数学推导、kernel/源码对应、实验与局限。已有解释去重，新证据修正相关论断，独有例子、手工内容和来源保留；不要在末尾按会话追加另一篇文章，也不要因长度或技术专题另开 sidecar。
- 论文配套的源码解读归入同一主文章，并注明代码版本及与论文的差异。跨论文通用原理、独立项目实践或用户明确要求的独立交付物可以另存，但不能只是换标题重复同一论文。合并旧文档时同步修正索引、正文链接和内部重定向；索引保留一个主入口，细节用文内锚点导航。
- Zotero 保存阅读时的高亮、翻译与随手批注，正式笔记按问题和机制组织，不默认收录完整标注导出。可以先记录已理解的局部问题，随阅读补充对应段落；不把有标注等同于已读，也不为未读部分填充结论。
- 讲清 **Background、Insights、Design、Evaluation**：论文解决什么问题，已有方法的限制是什么；关键洞察如何导出设计；方法的组成、数据流和关键公式；实验如何支撑结论及其局限。可以按更便于理解的顺序组织，不机械照搬论文章节。
- 保留影响理解或复现结论的重要细节，尤其是非显然的设计取舍、算法步骤、kernel 组织、训练或推理路径。判断细节是否重要，要看它是否改变机制、成本、实验解释或适用范围。例如阅读 MiniMax Sparse Attention 时，forward kernel 的设计和是否采用 Attention Sink 的讨论都不能仅用一句概括带过。
- 对解释关键机制或结果的论文图片，优先引入**原图**，使用仓库约定的相对路径保存并嵌入笔记。注明原论文的图号、来源及这张图说明了什么；自绘图可补充解释，但不要冒充论文原图。若原图无法取得，保留明确的原文图号和链接。
- 对重要且措辞精确的细节，引用必要的**短段原文**，标明章节或页码，并紧接着解释其含义；避免大段照录。对公式、算法和图中的符号，核对原文定义，不凭印象改写。
- 记录实验时写出问题、设置、指标、基线、关键结果与解释。明确区分作者报告的事实、自己的推论和证据无法确定的部分。

## 理论学习笔记

- 先说明要解决的问题、前提和符号，再给出推导的关键步骤与结论。检查下标、形状、符号、归一化系数及适用条件。
- **每段理论推导都配一个算得出来的例子**：代入具体数值、矩阵形状或小规模实例，展示从输入到结果的计算，并说明它验证了推导中的哪一步。例子应紧邻对应推导，不能只在文末集中罗列。
- 解释公式表达的机制和边界条件；不要用例子代替一般推导，也不要只列公式而不解释。

## 开源项目学习笔记

- 按完整功能或实现问题维护文章，同一主题跨 talk 整合更新；大型项目以项目名建目录，目录下按独立专题或子系统命名文件和标题，不把第一篇专题文章命名为整个项目的主笔记。例如 `FlashMLA/dsa-sparse-attention.md` 保存 DSA 实现，后续其他专题另建文件。同一个 PR 中无执行依赖的修改不因此合成一条调用链。只有一篇正文时，导航直接链接该专题；形成多个专题后再由有实质内容的项目总览组织，避免单链接中转页或空白占位页。重命名时同步索引、交叉链接和 Issue 中的主笔记入口。
- 以实际源码为依据，记录所分析的仓库版本或提交。先定位入口，再沿真实调用链或数据流 **step by step** 展开：每一步的输入、关键状态、执行的函数或模块、输出，以及进入下一步的条件。
- 讲清设计理念及取舍，并将其对应到具体实现。引入关键源码片段和文件、函数或行号链接，解释代码如何完成这一环节；不要只列文件名、贴大段源码或把阅读顺序当成运行流程。
- 用户要求 system overview 或 kernel design 图时，先读 [Kernel design 绘图参考](references/kernel-design-figures.md)，实际打开其中适合当前问题的论文原图；需要其他表达方式时，再从 Zotero 检索同类论文并看图。以论文机制图的张量表达、空间层次、鲜明配色和排版作为交付标准，复杂图优先用 draw.io 或 PowerPoint 等工具并交付可编辑源文件。图中用矩阵、token 条带、稀疏区域、存储边界和必要的泳道直接表达实现，避免把正文换成大量文字框。按参考文档选择图型、核对语义并渲染检查，不将加载交叠画成已证实完全隐藏延迟。
- 记录重要的数据结构、控制分支、边界情况和实现限制。若论文或文档的设计与当前代码不同，明确写出差异及其依据，不把设想当成已实现功能。

## 通用表达要求

- 按理解上的依赖关系组织内容，使用能说明内容的标题；不强制套用固定目录。
- 在首次需要时定义术语与符号，说明可能引起歧义的假设、维度和量的含义。
- 从学习讨论中提炼有复习价值的知识点和已澄清的误解，不把对话、进度汇报或鼓励性话语抄进笔记。
- 正式笔记是知识性总结，不附加“下一步”“下一次讨论”“后续练习”“待续”等面向后续学习、会话或实施的行动安排。这类建议留在讨论中；只有用户明确要求保存学习计划或任务清单时，才写入相应的独立文档。
- 保留已确认的结论、机制、适用条件、证据局限及相关工作。论文原文的未来工作、算法中的下一步和复现所需的环境或命令不属于个人行动计划；混合段落只删除行动安排，不能把同段的知识一并删掉，也不能只换标题而保留待办内容。
- 来源说明以支撑正文所需的简短引用为限，优先贴近相关论断或图注。不要添加“原图与来源”、逐图来源对照表、图片数量、裁切/DPI/哈希、抓取归档流程或冗长的整理声明。保留必要的原文链接、图号和影响结论的版本信息；需要区分 AI 补充或个人推论时用简短标注，不反复解释整理过程。
- 开头直接进入问题、定义、机制或核心结论，不添加“AI 整理”“本次核对”“本文依据……”“基于……整理”等编辑性开场白，也不逐段标“原文要点”“补充解释”。必要引用贴近具体内容；版本、实验设置、代码未经验证等实质性限制放在对应段落，个人推论在具体论断处明确标注。不能将长声明缩短成一行通用声明后继续保留。
- 永远不要向正式笔记、索引、目录、侧栏或自动生成的阅读页面加入导入与迁移台账：包括“已下载资料”、PDF/截图数量、GitHub issue 归档清单、外部文章迁入记录、Zotero 阅读进度专区、按翻译或来源平台分组的迁入入口、旧分类到新分类的对照，以及整理日期、搬运过程和重复条目合并说明。不得改名或缩短后保留，也不得另建来源汇总页放回导航。按知识主题提供笔记、论文和必要参考资料的入口；引用只用于支撑具体知识，阅读状态在对应论文条目中维护。旧链接兼容由内部重定向处理，不展示成正文。
- 用准确、直接的语言表达；删去重复内容和超出证据范围的结论。

## 编辑与检查

- 保留用户与任务无关的内容和改动。仅在仓库约定需要时更新索引或交叉链接，避免顺手重组其他文件。
- 对照用户骨架复核：个人判断和疑问是否被无依据地覆盖，新增段落是否解决具体缺口，事实、用户推论与 AI 补充是否可区分。交付时指出实质性纠正和仍需判断的疑点，不把文章写得完整当作用户已经理解或读完的依据。
- 完成前检查内容是否符合本次要求，理论推导是否逐一配有例子，论文原图与引文的出处是否准确，项目步骤是否与源码吻合，本地链接是否有效。
- 逐节复核：读者能否解释为什么需要这一设计、它如何工作、付出什么代价、证据支持到哪里；检查章节间的依赖是否真实、表格和代码前是否已交代对象含义。缺少依据时缩小结论范围，不靠重复提醒或继续压缩来掩盖解释缺口。
