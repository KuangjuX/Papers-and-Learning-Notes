# 撰写学习笔记

写出脱离原始对话也能独立阅读的笔记。这个仓库主要保存论文、理论学习和开源项目学习笔记。先判断本次属于哪一类，再应用对应规则；混合主题可以组合使用。以用户**本次**指定的主题、深度和范围为准，不把上一篇笔记的内容取舍当成通用要求。

## 确定范围

在本仓库新增或更新正式笔记时，先执行根目录 `AGENTS.md` 的 Issue 与 PR 工作流：创建或复用 Issue，再在独立分支编辑，通过关联 PR 合并；未读完论文的 Issue 跨多次 talk 和 PR 保持打开。

1. 确认这篇笔记要解释什么、依据哪些材料。整理现有笔记时先读原文；涉及论文时核对原论文及其附录，涉及项目时核对实际源码与版本。
2. 查看相邻笔记和仓库约定，确定存放位置、语言、链接方式与详略。若用户本次要求与既有习惯不同，以本次要求为准。
3. 根据学习目标选择内容。理论、数学推导、代码、实验、实现细节、例子与局限都可能有用；是否保留由本次任务和材料决定，不因另一篇笔记采用过某种写法就照搬。

## 论文笔记

- **一篇论文对应一篇持续更新的正式文章**。不同 talk、会话、来源或讨论主题不是新建笔记的理由。保存前用论文标题、别名、arXiv/DOI 或 Zotero key 检索主题索引和已有文件，确定唯一主笔记；仅当确实不存在时创建。
- 新讨论按理解依赖整合进已有章节：背景与问题、洞察与设计、数学推导、kernel/源码对应、实验与局限。已有解释去重，新证据修正相关论断，独有例子、手工内容和来源保留；不要在末尾按会话追加另一篇文章，也不要因长度或技术专题另开 sidecar。
- 论文配套的源码解读归入同一主文章，并注明代码版本及与论文的差异。跨论文通用原理、独立项目实践或用户明确要求的独立交付物可以另存，但不能只是换标题重复同一论文。合并旧文档时同步修正索引、正文链接和内部重定向；索引保留一个主入口，细节用文内锚点导航。
- Zotero 保存阅读时的高亮、翻译与随手批注，正式笔记按问题和机制组织，不默认收录完整标注导出。可以先记录已理解的局部问题，随阅读补充对应段落；不把有标注等同于已读，也不为未读部分填充结论。
- 讲清 **Background、Insights、Design、Evaluation**：论文解决什么问题，已有方法的限制是什么；关键洞察如何导出设计；方法的组成、数据流和关键公式；实验如何支撑结论及其局限。可以按更便于理解的顺序组织，不机械照搬论文章节。
- 保留影响理解或复现结论的重要细节，尤其是非显然的设计取舍、算法步骤、kernel 组织、训练或推理路径。判断细节是否重要，要看它是否改变机制、成本、实验解释或适用范围。例如阅读 MiniMax Sparse Attention 时，forward kernel 的设计和是否采用 Attention Sink 的讨论都不能仅用一句概括带过。
- 对解释关键机制或结果的论文图片，优先引入**原图**，使用仓库约定的相对路径保存并嵌入笔记。注明原论文的图号、来源及这张图说明了什么；自绘图可补充解释，但不要冒充论文原图。若原图无法取得，保留明确的原文图号和链接。
- 对重要且措辞精确的细节，引用必要的**短段原文**，标明章节或页码，并紧接着解释其含义；避免大段照录。对公式、算法和图中的符号，核对原文定义，不凭印象改写。
- 记录实验时写出问题、设置、指标、基线、关键结果与解释。明确区分作者报告的事实、自己的推论和证据无法确定的部分。

## 理论学习笔记

- 先说明要解决的问题、前提和符号，再给出推导的关键步骤与结论。检查下标、形状、符号、归一化系数及适用条件。
- **每段理论推导都配一个算得出来的例子**：代入具体数值、矩阵形状或小规模实例，展示从输入到结果的计算，并说明它验证了推导中的哪一步。例子应紧邻对应推导，不能只在文末集中罗列。
- 解释公式表达的机制和边界条件；不要用例子代替一般推导，也不要只列公式而不解释。

## 开源项目学习笔记

- 按完整功能或实现问题维护文章，同一主题跨 talk 整合更新；大型项目按独立子系统分篇，由项目总览组织。同一个 PR 中无执行依赖的修改不因此合成一条调用链。只有一篇正文的项目直接以正文作为入口，避免单链接中转页；不将只有标题或待开发文字的页面列入正式导航。
- 以实际源码为依据，记录所分析的仓库版本或提交。先定位入口，再沿真实调用链或数据流 **step by step** 展开：每一步的输入、关键状态、执行的函数或模块、输出，以及进入下一步的条件。
- 讲清设计理念及取舍，并将其对应到具体实现。引入关键源码片段和文件、函数或行号链接，解释代码如何完成这一环节；不要只列文件名、贴大段源码或把阅读顺序当成运行流程。
- 记录重要的数据结构、控制分支、边界情况和实现限制。若论文或文档的设计与当前代码不同，明确写出差异及其依据，不把设想当成已实现功能。

## 通用表达要求

- 按理解上的依赖关系组织内容，使用能说明内容的标题；不强制套用固定目录。
- 在首次需要时定义术语与符号，说明可能引起歧义的假设、维度和量的含义。
- 从学习讨论中提炼有复习价值的知识点和已澄清的误解，不把对话、进度汇报或鼓励性话语抄进笔记。
- 正式笔记是知识性总结，不附加“下一步”“下一次讨论”“后续练习”“待续”等面向后续学习、会话或实施的行动安排。这类建议留在讨论中；只有用户明确要求保存学习计划或任务清单时，才写入相应的独立文档。
- 保留已确认的结论、机制、适用条件、证据局限及相关工作。论文原文的未来工作、算法中的下一步和复现所需的环境或命令不属于个人行动计划；混合段落只删除行动安排，不能把同段的知识一并删掉，也不能只换标题而保留待办内容。
- 来源说明以支撑正文所需的简短引用为限，优先贴近相关论断或图注。不要添加“原图与来源”、逐图来源对照表、图片数量、裁切/DPI/哈希、抓取归档流程或冗长的整理声明。保留必要的原文链接、图号和影响结论的版本信息；需要区分 AI 补充或个人推论时用简短标注，不反复解释整理过程。
- 开头直接进入问题、定义、机制或核心结论，不添加“AI 整理”“本次核对”“本文依据……”“基于……整理”等编辑性开场白，也不逐段标“原文要点”“补充解释”。必要引用贴近具体内容；版本、实验设置、代码未经验证等实质性限制放在对应段落，个人推论在具体论断处明确标注。不能将长声明缩短成一行通用声明后继续保留。
- 永远不要向正式笔记、索引、目录、侧栏或自动生成的阅读页面加入导入与迁移台账：包括“已下载资料”、PDF/截图数量、GitHub issue 归档清单、外部文章迁入记录、Zotero 阅读进度专区、按翻译或来源平台分组的迁入入口、旧分类到新分类的对照，以及整理日期、搬运过程和重复条目合并说明。不得改名或缩短后保留，也不得另建来源汇总页放回导航。按知识主题提供笔记、论文和必要参考资料的入口；引用只用于支撑具体知识，阅读状态在对应论文条目中维护。旧链接兼容由内部重定向处理，不展示成正文。
- 用准确、直接的语言表达；删去重复内容和超出证据范围的结论。

## 编辑与检查

- 保留用户与任务无关的内容和改动。仅在仓库约定需要时更新索引或交叉链接，避免顺手重组其他文件。
- 完成前检查内容是否符合本次要求，理论推导是否逐一配有例子，论文原图与引文的出处是否准确，项目步骤是否与源码吻合，本地链接是否有效。
- 检查全文，尤其是文章末尾，移除对后续会话、阅读、练习或开发工作的安排；以知识、证据范围或必要来源自然收尾，不强行添加行动建议。
- 检查文章开头和正文中的编辑性说明，删除与知识内容无关的来源、图片、核对和整理过程描述；只保留必要引用与影响结论的限制，避免文末重复说明。
- 检查总览、主题索引、目录和生成脚本是否含导入或迁移台账；清理时同时修正生成逻辑，确认再次同步或构建不会恢复这些内容。
- 向用户说明笔记写在何处、改了什么，以及尚存的实质性不确定之处。
- 按 `AGENTS.md` 完成 PR 与 Issue 收尾，并提供对应链接。未读完或状态不确定的论文用 `Refs` 关联，避免 PR 或提交信息自动关闭 Issue；确认合并后再清理工作分支。
