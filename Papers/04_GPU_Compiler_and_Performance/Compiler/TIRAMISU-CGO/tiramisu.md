# TIRAMISU：调度语言、四层 IR 与论文论证方式

Tiramisu 将算法、执行调度、数据布局和通信分开表示，让用户通过调度命令控制代码生成。它要解决的困难是：多面体模型能够表达复杂变换，但自动搜索未必选得出高性能组合；不同硬件还需要不同的内存与通信策略。[原论文](https://arxiv.org/abs/1804.10694)，CGO 2019。

## 从 GEMM 的优化组合引出调度语言

GEMM $C=\alpha AB+\beta C$ 的高性能实现同时涉及循环融合、两级 tiling、向量化、展开、array packing、register blocking 和预取，还要区别完整 tile 与边界 tile。GPU 路径进一步需要合并访存、管理 global/shared/register 数据移动并插入同步。

论文 §I 用这一实例说明：能表达某项变换，与能组合出好的程序，是两个问题。Polly、Pluto 等自动调度器在论文所比较的版本中受搜索范围和成本模型限制；AlphaZ、CHiLL 让用户控制调度，却没有覆盖作者需要的分布式划分、发送接收和同步命令。

Tiramisu 因而选择“算法 + 显式调度命令”的接口。它支持多核 CPU、CUDA GPU 和分布式机器；FPGA 后端由配套工作介绍，不能将所有后端都视为本篇相同范围的评测。适用算法主要是稠密数组上的数据并行循环，例如图像处理、stencil、线性代数和深度学习算子。

## 算法先描述依赖，调度再决定执行方式

Tiramisu 是嵌入 C++ 的 DSL，也可以作为其他 DSL 的代码生成目标。用户为每个 computation 指定迭代域和表达式，用显式 producer–consumer 关系连接计算，暂不指定内存位置。[原论文 §III](https://arxiv.org/pdf/1804.10694)

论文 blur 示例包含先横向计算 `bx`、再从 `bx` 计算 `by` 两步。下面以三点均值的简化伪代码展示两阶段依赖；区间右端不包含，输出尺寸缩小，不补边界：

```text
for (i in 0..N)
    for (j in 0..M-2)
        for (c in 0..3)
            bx[i][j][c] = (in[i][j][c]+in[i][j+1][c]+in[i][j+2][c])/3
for (i in 0..N-2)
    for (j in 0..M-2)
        for (c in 0..3)
            by[i][j][c] = (bx[i][j][c]+bx[i+1][j][c]+bx[i+2][j][c])/3
```

该版本的算法控制流限于 `for` 和条件语句，不能直接表达 `while`、提前退出或 `goto`。这项边界使迭代域与依赖能够进入多面体分析。

调度命令分为四类：

| 控制对象 | 命令及作用 |
|---|---|
| 循环变换 | tiling、splitting、shifting 等仿射变换；`C.tile(i,j,32,32,i0,j0,i1,j1)` 将二维循环分成 32×32 tiles |
| 硬件映射 | 并行化、向量化、GPU block/thread 映射；`C.vectorize(j,4)` 将内层映射为四个向量 lanes |
| 数据 | 分配数组，选择 host/device/shared/local memory，安排拷贝并指定数组访问 |
| 通信与同步 | barrier、send/receive，以及通信时机、粒度和同步/异步方式 |

高层命令用于常见情形，低层命令提供更细控制。用户同时承担调度选择的责任：可控性与跨平台表达能力，并不等于自动获得最优调度。

## 四层 IR 为什么按这个顺序下降

若一开始用内存地址连接语句，就会引入与布局相关的依赖。后续调度为了改变计算次序和目标硬件，可能不得不先撤销布局；shared-memory buffer 大小、发送范围与同步位置又依赖 tiling 和执行映射。Tiramisu 将这些决策按依赖顺序分层。[原论文 §IV-A](https://arxiv.org/pdf/1804.10694)

| 层 | 明确的信息 | 暂时不决定的信息 |
|---|---|---|
| 算法 | 计算表达式、迭代域、producer–consumer 关系 | 执行次序、存储位置 |
| 计算调度 | 计算先后及哪个处理器计算哪个值 | 具体数据布局 |
| 数据布局 | 中间值在消费前保存在哪里 | 最终通信与同步操作 |
| 通信 | 搬运、发送接收与同步 | 前三层的选择已可用于推导需求 |

分层的价值是避免后面的 pass 反复推翻过早作出的决定，而非单纯增加 IR 数量。例如先确定 tile 和线程映射，才能确定该 tile 需要搬入 shared memory 的数据范围及 barrier 位置。

## 用整数集合和映射表达迭代与访问

整数集合描述迭代域，映射描述访问关系或迭代变换。原文的集合示例为：

$$
\{S(i,j):1\le i\le3\land1\le j\le2\}.
$$

它对应六个点 $(1,1),(2,1),(3,1),(1,2),(2,2),(3,2)$，无需逐个列出。映射

$$
\{S_1(i,j)\to S_2(i+2,j+2):1\le i\le3\land1\le j\le2\}
$$

把 $(1,1)$ 映到 $(3,3)$，把 $(3,2)$ 映到 $(5,4)$。Tiramisu 用 ISL 实现这些集合与映射，论文也沿用 ISL 记法。[原论文 §IV-B](https://arxiv.org/pdf/1804.10694)

## 相关工作如何界定表达能力

论文 §II 的分类对应不同限制，而非仅列系统名称：

- **自动调度的多面体编译器。** PENCIL、Pluto、Polly、Tensor Comprehensions、PolyMage 等强调自动化；作者讨论的是所比较实现的优化覆盖与成本模型限制。Tiramisu 用显式命令交还选择权。
- **带调度语言的多面体框架。** AlphaZ、CHiLL、URUK 能表达仿射变换；本文强调的差别是分布式通信、同步与数据放置的控制，而非它们完全不能生成不同硬件的代码。
- **带调度语言的非多面体框架。** Halide 的 interval 表示难以精确表示非矩形迭代域，可能高估边界或通信量；论文还讨论 skewing、循环依赖图及依赖分析的差异。`compute_with` 的限制针对第二个循环消费第一个循环结果等具体情形，不能概括为“Halide 不支持循环融合”。TVM、DSP Halide 扩展、POET 和 GraphIt 则分别提供了不同的表示、存储控制、语法变换或图应用调度能力。
- **函数式并行表示。** Delite、NOVA、Lift 以 map/reduce/scan 等模式表达并行，与多面体中的复杂仿射变换可以互补。

这些比较绑定论文发表时的版本和分析范围，不是对后续编译器能力的永久判断。

## 论文如何把问题、设计与证据串起来

**个人阅读角度：编译器论文的论证写法。** 摘要先用 “a polyhedral framework” 确定系统类别，再交代目标平台、调度语言、四层 IR 和实验对象。它以短篇幅覆盖整条论证链，但具体能力仍需正文解释。

引言从硬件复杂性收敛到 GEMM 的具体优化组合，再比较自动调度与手动调度语言各自缺失的能力，最后引出 Tiramisu。GEMM 用来说明动机，blur 示例则用于解释 DSL；两者承担不同作用。

原笔记把 Related Work 理解为背景章节：分类的目的在于明确现有方法还不能处理哪些约束，让后面的设计有针对性。原有“论文强调自己、批评他人”的写作观察，更具体地体现为：作者围绕表达能力、调度控制和通信支持建立比较，阅读时仍需检查例子和证据是否足以支持比较。

DSL 章节先限定适用范围，再说明算法与调度接口；IR 章节先解释过早确定布局的困难，再引入分层和集合表示。这种安排让读者先知道抽象要解决什么，再学习定义。

论文报告在所测深度学习与线性代数 kernels 中，相对 Intel MKL 最高 2.3×，并比较多核、GPU、分布式图像处理任务。这里的数字是作者在相应基准上的结果，不是全部算子或平台的统一收益；该摘记聚焦接口、IR 与论证结构，未展开逐项实验归因。[原论文 §I、Evaluation](https://arxiv.org/pdf/1804.10694)
